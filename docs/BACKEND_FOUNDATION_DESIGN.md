## 最初にFEへ提供する範囲

1. ユーザー登録。
2. ログイン。
3. ログイン中の自分の情報取得。
4. ログアウト。
5. 上記のGraphQLスキーマ、操作例、応答・エラー例、FE用の型生成手順。

プロフィール編集、OAuth、通知、フレンドなどは後続機能として接続先を整理する。最初の完成判定は上記の範囲で行う。

## リーダーと先に合わせたいこと

| 議題 | 初案 | 判断による影響 |
|---|---|---|
| 最初に接続する画面 | 登録・ログイン・ログイン後の本人表示 | FEが先に必要とするAPIと実装順が決まる |

表示名・パスワードの文字数、メールの正規化ルール、メール確認の要否は未確定。入力項目と画面の要望を合わせた後、FE/BE共通のルールとして定義する。

## GraphQLの入出力案

操作名と型名は提案。code-firstのTypeScript定義を正本とし、GraphQLスキーマを生成する。

| 操作 | 入力 | 正常時の結果 | 補足 |
|---|---|---|---|
| `signUp` | `email`、`password`、`displayName` | `AuthPayload` | 提案では登録とセッション作成後にCookieを設定する |
| `signIn` | `email`、`password` | `AuthPayload` | Cookieを設定する。JWTを応答本文には含めない |
| `me` | ユーザーIDの指定なし。Cookieで認証 | `Viewer` または `null` | 未ログイン・期限切れ・失効済みは `null`。DB障害等を未ログイン扱いにはしない |
| `signOut` | ユーザーIDの指定なし。Cookieで認証 | `success: true` | 現在のセッションを失効させ、Cookieを解除する。既に未ログインでも成功とする |

| 型 | 項目案 | 公開先 |
|---|---|---|
| `Viewer` | `id: ID!`、`displayName: String!`、`email: String!` | ログイン中の本人 |
| `PublicUser` | `id: ID!`、`displayName: String!` | 他人に見せる場面。必要なAPIを追加する段階で実装 |
| `AuthPayload` | `user: Viewer!` | 登録・ログインに成功した本人 |

`!` はnullにならない値を表す。パスワードハッシュやセッションの内部情報は、どの公開型にも含めない。

後続のプロフィール更新では「項目を送らない＝変更しない」を基本にする。任意項目の削除には `null` を使う案とし、空文字の扱いは項目ごとに定義する。必須の表示名は `null` を受け付けない。

### エラーとFEの表示

アプリが返すエラーは `errors[].extensions.code` で区別する案とする。項目別エラーはフィールド名と検証コードを返し、FEが表示言語に合わせた文言へ変換する。GraphQL自体の構文・型エラーの扱いも、基盤導入時に確認する。

| コード案 | 意味 | FE側の対応例 |
|---|---|---|
| `VALIDATION_FAILED` | 文字数・形式などの入力違反 | 対象の入力欄に説明を表示 |
| `REGISTRATION_FAILED` | メール重複などで登録できない | 登録を完了できない旨と、ログイン等の導線を表示 |
| `INVALID_CREDENTIALS` | ログイン情報が正しくない | メールの存在・パスワード誤りを区別しない表示 |
| `UNAUTHENTICATED` | 認証が必要な操作への未認証要求 | ログインへ案内。`me` は上記のとおり `null` |
| `FORBIDDEN` | 認証済みだが操作権限がない | 操作できない旨を表示 |
| `INTERNAL_SERVER_ERROR` | 予期しない障害 | 再試行の案内。内部例外やSQLを公開しない |

FEへスキーマ・操作例・仮の応答を先に渡せば、BE完成前でも画面を進められる。型生成が成功することと、実際のAPIが動くことは別に検証する。

## DBの論理設計案

既存の [全体概要 §6 のDB関係図](PROJECT_OVERVIEW.md) の `users` を各機能の接続点とする。ここでは保存する情報と関係を定める。IDのDB型・生成方法、具体的なSQLはマイグレーション作成前に決める。

| テーブル案 | 主な保存項目 | 制約と理由 |
|---|---|---|
| `users` | 不変のID、メール、表示名、作成・更新日時 | IDは主キー。合意した正規化ルールに従うメールに一意制約を設け、同時登録でも重複を防ぐ。表示名は識別に使わない |
| `password_credentials` | ユーザーID、パスワードハッシュ、更新日時 | ユーザーIDを主キー兼外部キーにし、ユーザー1人につき最大1件。認証情報をプロフィールから分離し、将来パスワードを持たないOAuthユーザーにも対応できる構成にする |
| `auth_sessions` | セッションID、ユーザーID、有効期限、失効日時、作成日時 | ユーザーに対して複数件。JWTにセッションIDを含め、検証時に期限・失効状態・ユーザーとの対応も確認する案。JWT本文の保存は不要 |

```text
users 1 ── 0..1 password_credentials
      1 ── 0..N auth_sessions
      1 ── 0..N oauth_accounts（後続）
```

初期のメール登録では `users` と `password_credentials` を必ずセットで作る。一連のDB更新をトランザクションで扱い、片方だけが残ることを防ぐ。

日時はタイムゾーンを扱える型を使う。`auth_sessions.user_id` は外部キーと検索用インデックスを設ける。主キー・一意制約で検索が支えられる列には、同じインデックスを重複追加しない。

将来の `oauth_accounts` はプロバイダーとそのユーザー識別子で関連づける。メールが同じという理由だけで既存アカウントに自動連結する設計にはしない。

ユーザー削除時の対局・メッセージの保持や匿名化は、各担当とGDPR対応の範囲で決める。全関連データを一律に連鎖削除する方針は置かない。

## 認証と対局担当への渡し方

```text
FEの要求と認証Cookie
  → Auth側がJWTの署名・期限とセッションを検証
  → 検証済みのユーザーIDを処理へ渡す
  → Match側が対局参加者・手番・受け付けてよい操作かを確認
  → エンジンが合法手を判定
```

FEが指定したユーザーIDを本人確認には使わない。Auth側は「誰か」を保証し、Match側はそのユーザーを対局の黒・白に対応づける。エンジンの `Move.player` にクライアントの申告をそのまま渡さない。

時間切れの確定や合意引き分けはサーバー側の責務であり、クライアントがエンジンの全操作を直接指定できるAPIにはしない。根拠は [軍儀ルール §11.6・§11.7](GUNGI_RULES.md)。

JWTをCookieで扱うため、HTTPS・HttpOnlyに加えて、Cookieの送信条件とCSRF対策を認証実装に含める。Cookieの解除だけで完了とせず、対応するセッションも失効させる。パスワード・JWTをログへ出さない。

次の接続条件はkoyonと合わせる。

- Next.jsのSSRから本人情報を取得するときのCookieの受け渡しと、利用者ごとの情報を共有キャッシュに載せない扱い。
- Socket.IOとGraphQL Subscriptionsの用途分担。既存資料では記述が揃っていない。
- リアルタイム接続で同じ認証判定を使う方法と、接続中にログアウト・期限切れになった場合の扱い。
- エンジンのデータ形式を引き継ぐ範囲と、対局状態・棋譜の保存責任。Auth側ではゲームルールを再実装しない。

マイグレーションは開発用DBで確認する。共有DBへの適用は対象と既存データへの影響を確認して行う。チームに共有済みの変更は、新しいマイグレーションで進める。

## 実装を読む順番

登録機能では、入力例 → Resolver → Service → Prisma → DB制約 → 応答の順に追う。認証が必要な操作では、その前にGuardの本人確認を読む。

各実装単位で、次を説明できることを理解確認の目標にする。

- 何を受け取り、何を返すか。
- なぜそのテーブル・列・関係が必要か。
- どこで入力・本人・権限を確認するか。
- 失敗や同時操作が起きたとき、何が保存され、何が拒否されるか。
- テストがどの仕様を確かめているか。

## 相談用のメッセージ案

> BE基盤は既存のNestJS・GraphQL code-first・Prisma方針で進めたいです。まず登録・ログイン・自分の情報取得・ログアウトを最初の接続範囲として、スキーマと型生成を早めに用意する案です。
>
> 登録項目はメール・パスワード・表示名、表示名は重複可と考えています。一意のユーザー名が必要か、登録後すぐログイン状態にしてよいか、FEで先に接続したい画面があるかを合わせたいです。
>
> DBは既存のusers中心の関係図を引き継ぎ、認証情報とログインセッションを分ける案です。対局側へは検証済みのユーザーIDを渡す想定なので、SSR・リアルタイム通信との認証のつなぎ方も相談したいです。
