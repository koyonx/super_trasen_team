# 軍儀 (Gungi) ルール仕様書 — エンジン実装準拠版

本書は `packages/gungi-engine` が **1:1 で実装する唯一の正式仕様** である。
エンジンのテスト (`packages/gungi-engine/src/*.spec.ts`) は本書のセクション番号（例: `§5.3`）を
`describe` 名に含めて対応付けている。ルールを変更する場合は **本書 → テスト → 実装** の順に更新すること。

## 準拠ルールセット

- **ルールの権威は [jwyce/gungi.io](https://github.com/jwyce/gungi.io)（オンライン対戦サイト gungi.io）とする。**
- gungi.io リポジトリ自体はゲームロジックを持たず、サーバーが npm パッケージ
  **`gungi.js@1.0.20`**（`server/package.json` で固定）に全ルール判定を委譲している。
  したがって本書は **`gungi.js@1.0.20` のソースコード**（`src/gungi.ts`, `src/utils/move_gen.ts`,
  `src/utils/stockpile_move_gen.ts`, `src/utils/helper.ts`）を一次資料とし、文章より **コードを優先** する。
- 参照したバージョン:
  - gungi.io: commit `33ead0ad31dac255e1e4e057eceb177e69e651f5`（2026-01-06）
  - gungi.js: npm `1.0.20`（reddit の u/Zaneme・u/squal777 による改訂ルールの実装）
- jwyce の新しい `gungi.js`（公式ルールブック準拠の 2.x 系）は **参照しない**。
- gungi.io のコードで未定義の点、またはアプリ側で決める点には **⚠要チーム確認** を付けた。一覧は §13。

## §1 用語

| 用語 | 意味 |
|---|---|
| 黒 / 白 | 黒 (`black`) = 配置フェーズの先手。白 (`white`) = 対局フェーズの先手（§9.4） |
| 段 (tier) | スタック内での高さ。最下段が 1 段目。最大 3 段 |
| スタック（ツリー） | 1 マスに積まれた駒の列（下→上）。高さ = 駒数 |
| 最上段の駒 (top) | スタックの一番上の駒。そのマスの「持ち主」はこの駒の所有者とみなす |
| 持ち駒 (hand) | まだ盤上に出していない自分の駒（gungi.io の stockpile）。取られた駒は持ち駒にならない（§6.4） |
| ツケ | 駒を他の駒（敵味方問わず）の上に重ねること |
| 新 (あらた) | 対局フェーズで持ち駒を盤上に打つこと（gungi.io の game phase の `place`） |
| 擬態 | 2 段目以上の謀が、真下の駒の動きを借りること（§7） |

## §2 盤と座標

### §2.1 盤

- 9×9 = 81 マス。
- 座標は 0 始まり: `file`（筋, 0..8）, `rank`（段列, 0..8）。
- **rank 0 が黒の最奥列、rank 8 が白の最奥列**。
- gungi.io の表記 `R-F`（1 始まり、黒が rank 7..9 側）との対応: `rank = 9 − R`, `file = F − 1`。
  全駒の動きは左右対称なので、筋の向きの違いはルールに影響しない。

### §2.2 前方向

- 黒の前方 = `rank` が増える方向 (+1)。
- 白の前方 = `rank` が減る方向 (-1)。
- 駒の動きの定義（§5）は「自分から見た相対座標 (横 df, 前 dr)」で書く。白の場合は盤上で 180° 回転（df・dr とも符号反転）して適用する。

### §2.3 自陣（配置フェーズで置ける範囲）

- 黒の自陣 = rank 0, 1, 2
- 白の自陣 = rank 6, 7, 8

### §2.4 新の範囲（対局フェーズで打てる範囲）

- 黒 = rank 0..5（自分側 6 列）
- 白 = rank 3..8（自分側 6 列）

### §3.2 駒の成り

- 成りは存在しない。

### §3.3 盤上の駒数上限

- 各プレイヤーが盤上に置ける自分の駒は **最大 26 枚**（下段に埋もれた駒も数える）。
- 26 枚に達している間は配置（§9）・新（§8）ができない。取られて減れば再び打てる。

## §4 段とスタック

### §4.1 最大段数

- 1 マスのスタックは最大 **3 段**。4 段目を作る着手（ツケ・新・配置）はすべて不可。

### §4.2 動かせる駒

- 動かせるのは **各スタックの最上段の駒のみ**。下にある駒は（自分の駒でも）動かせず、利きも持たない。
- 最上段の駒が動く・取られると、その下の駒が新たな最上段となる。

### §4.3 駒の段

- 駒の「段」= その駒がスタック内で何番目にあるか（1..3）。
- 駒の動ける範囲は、**移動開始時点のその駒の段** によって決まる（§5.3 の段別表）。

### §4.4 帥に関する制限

- **帥の上には、いかなる駒もツケられない**（移動・新・配置のいずれでも）。したがって帥は常に最上段にある。
- 帥自身は他の駒の上にツケてよい。

### §4.5 砦に関する制限

- **砦は他の駒の上に乗れない**。砦のツケは不可、砦の配置・新は空マスのみ。したがって砦は常に 1 段目にある。
- 他の駒が砦の上にツケること・砦の上に配置/新をすることは可能。

## §5 駒の動き

### §5.1 動きの種類

| 種類 | 定義 |
|---|---|
| 歩 (step, 範囲 n) | 指定方向へ 1..n マス進める。途中のマスに駒（敵味方・高さ問わず）があればそれより先へは進めない。駒があるマス自体へは §6 の条件で着手可 |
| 走 (slide) | 指定方向へ盤端まで何マスでも進める。遮断は「歩」と同じ |
| 跳 (jump) | 指定オフセットのマスへ **途中の駒を飛び越えて** 直接着地する |
| 経由跳 (jump via) | 指定オフセットへ着地する。ただし指定の経由マスが **空** の場合に限る（大の 3 段目のみ） |
| 擬態 (mimic) | 謀の 2・3 段目。§7 参照 |

段による一律の範囲拡張は **ない**。各段の動きは §5.3 の表で個別に定義される。

### §5.2 表記

- F=前, B=後, L=左, R=右, FL/FR=斜め前, BL/BR=斜め後。
- 「8 方向」= F, B, L, R, FL, FR, BL, BR。「斜め 4 方向」= FL, FR, BL, BR。「縦横 4 方向」= F, B, L, R。
- 跳のオフセットは (df, dr)、dr > 0 が前。

### §5.3 各駒の段別の動き（自分から見た相対座標）

| §番号 | 駒 | 1 段目 | 2 段目 | 3 段目 |
|---|---|---|---|---|
| §5.3.1 | 帥 | 8 方向 歩1 | 8 方向 歩1 | 8 方向 歩1 |
| §5.3.2 | 大 | F, FL, FR, L, R, B 歩1（金将型） | 8 方向 歩1 | 8 方向 歩1 ＋ 経由跳 (-1,+2) 経由 (-1,+1)、(0,+2) 経由 (0,+1)、(+1,+2) 経由 (+1,+1) |
| §5.3.3 | 中 | F, FL, FR, BL, BR 歩1（銀将型） | F, FL, FR, B, BL, BR 歩1 | 8 方向 歩1 |
| §5.3.4 | 小 | FL, FR 歩1 | F, FL, FR, BL, BR 歩1（銀将型） | F, FL, FR, L, R, B 歩1（金将型） |
| §5.3.5 | 侍 | 斜め 4 方向 歩1 | 跳 (±2, ±2) の 4 マス | 斜め 4 方向 走 |
| §5.3.6 | 馬 | 跳 (-1,0), (+1,0), (-1,+2), (+1,+2) | 跳 (-2,+1), (-1,+2), (+1,+2), (+2,+1) | 跳 (±1,±2), (±2,±1) の 8 マス |
| §5.3.7 | 忍 | F 歩1 | 斜め 4 方向 歩1 | 8 方向 走 |
| §5.3.8 | 砦 | 8 方向 歩1 | （同左） | （同左） |
| §5.3.9 | 兵 | F 歩1 | F, FL, FR 歩1 | F, FL, FR 歩1 |
| §5.3.10 | 砲 | 縦横 4 方向 歩1 | 縦横 4 方向 歩2 | 縦横 4 方向 走 |
| §5.3.11 | 弓 | 8 方向 歩1 | 跳: 自分から縦横とも 2 以内で、ちょうど距離 2 のマス（5×5 の外周 16 マス） | 跳: 距離ちょうど 3 のマス（7×7 の外周 24 マス） |
| §5.3.12 | 筒 | F 歩1 | F 歩2 | F 走 |
| §5.3.13 | 謀 | 8 方向 歩1 | 擬態（§7） | 擬態（§7） |

- 「距離」はチェビシェフ距離 `max(|df|, |dr|)`。
- 砦は §4.5 により常に 1 段目だが、仮に上段にあっても 8 方向 歩1 とする（gungi.js の実装どおり）。

## §6 盤上の着手（移動・取り・ツケ）

### §6.1 着手の種類

手番側は自分の最上段の駒を 1 つ選び、§5 で到達可能なマス（移動先）に対して次のいずれかを行う。

| 種類 | Move `type` | gungi.io | 移動先の条件 |
|---|---|---|---|
| 移動 | `move` | `move` | 移動先が空 |
| 取り | `capture` | `attack` | 移動先の最上段が **敵の駒** |
| ツケ | `stack` | `stack` | 移動先にスタックがある（最上段は敵味方どちらでもよい）、かつ §6.3 |

最上段が敵の駒であるマスに対しては、「取り」と「ツケ」の両方が選択肢になり得る。どちらを行うかは Move で明示する。

### §6.2 高さ条件はない

- 取り・ツケとも、**移動する駒の段と移動先スタックの高さの比較は行わない**。
  1 段目の駒が 3 段目の駒を取ることも、2 段のスタックにツケることもできる。

### §6.3 ツケの条件

- 移動先の高さ `< 3`（§4.1）。ツケた駒の段は `高さ + 1` になる。
- 移動先の最上段が帥でない（§4.4）。
- 動かす駒が砦でない（§4.5）。

### §6.4 取りの処理

- 移動先スタックの **最上段の 1 枚だけ** が取られる。
- 取った結果 **移動先が空になった場合のみ**、取った駒が移動先へ移る（1 段目になる）。
- 移動先にまだ駒が残る場合、取った駒は **元のマスに留まる**（手番は消費する）。
- 取られた駒はゲームから除外される（持ち駒にはならない）。取った側の `captured` 記録に残す。

例: 下から [白兵, 黒侍, 白大] のスタックを黒が取ると、白大だけが除外され [白兵, 黒侍] が残り、取った黒駒は元のマスのまま。

## §7 謀（擬態）

### §7.1 1 段目

- 8 方向 歩1。

### §7.2 2・3 段目

- 謀は **真下の駒**（敵味方問わず）の種類の動きを、**謀自身の段・謀自身の向き（所有者）** で行う。
  - 例: 2 段目の黒謀の下に白の大がある → 黒の「2 段目の大」（8 方向 歩1）として動く。
  - 例: 3 段目の謀の下に弓（2 段目）がある → 「3 段目の弓」として動く。
- 真下の駒が謀の場合:
  - 謀が 3 段目なら、さらにその下（1 段目）の駒の動きを 3 段目として借りる。
  - 謀が 2 段目なら（借りる駒がないので）8 方向 歩1。
- 擬態は利き（§10 の王手判定）にもそのまま適用する。

### §7.3 寝返りはない

- 旧仕様の寝返り（持ち駒を払って敵駒を自分の駒に替える）は gungi.io に存在しないため廃止。

## §8 新（持ち駒を打つ）

### §8.1 基本

- 対局フェーズで、手番側は着手の代わりに持ち駒を 1 枚盤上に打てる（Move `type: "drop"`）。1 手として数える。

### §8.2 打てる段列

- **§2.4 の自分側 6 列** のマスにのみ打てる（最前線ルールはない）。

### §8.3 打てるマス

次をすべて満たすマスに打てる。

- 空マス、または高さ `< 3` で最上段が帥でないスタック（**最上段が敵の駒でもよい**。取りは発生しない）。
- 砦は空マスのみ（§4.5）。
- 兵は、その筋（file）のどこか（どの rank・どの段でも）に **自分の兵がある場合は打てない**（二兵禁止）。
- 打つと盤上の自駒が 27 枚以上になる場合は打てない（§3.3）。

### §8.4 その他

- 打ち兵詰めは **禁止されない**（gungi.js では該当チェックがコメントアウトされている）。

---

## §9 初期配置フェーズ（ドラフト）

### §9.1 開始状態

- 盤は空。両者とも 38 枚すべてが持ち駒。手番は **黒**。

### §9.2 配置手 (`place`)

- 手番側は持ち駒を 1 枚、**自陣（§2.3）** のマスに置く。
- 置けるマスの条件は §8.3 と同じ（空マス、または高さ `< 3` かつ最上段が帥でないスタック。砦は空マスのみ。二兵禁止。26 枚上限）。
- **各プレイヤーの最初の配置は帥でなければならない。**

### §9.3 配置完了 (`finishPlacement`, gungi.io の `ready`)

- 手番側は配置の代わりに「済」を宣言できる。帥を置いていなければ宣言できない。
- 済を宣言したプレイヤーはそれ以降配置できない。もう一方のプレイヤーは、自分が済を宣言するまで **連続して** 配置を続ける。
- 持ち駒が残っていても、26 枚に達していても、自動では済にならない（必ず宣言が必要）。
- 配置しなかった駒は持ち駒として残り、対局中に新で使える。

### §9.4 手番の進行

- 両者とも未完了の間は交互に配置する（黒から）。
- 一方が完了済みなら、もう一方が連続して配置する。
- 両者完了で対局フェーズに移行し、**白から** 指す。

### §9.5 配置フェーズ中の王手

- 配置した駒の利きで相手の帥が攻撃されることがある（王手）。§10 の自殺手禁止は配置フェーズにも適用される:
  - 自分の帥が攻撃されたままになる配置・済宣言はできない。
  - 王手をかけられた側は、利きを遮る配置で解消しなければならない。解消できなければ詰み（§11.2）。

⚠要チーム確認 (R-2): 配置フェーズ中の王手・詰み・自殺手判定は gungi.js の汎用処理（全フェーズで合法手を自殺手フィルタする）による副作用で、意図された仕様かは不明。本仕様はコードどおり適用する。

## §10 禁じ手

### §10.1 自殺手（帥が攻撃される状態にする手）

- 着手後、**相手のいずれかの最上段の駒の到達可能マス（§5・§7）に自分の帥がある状態になる手は指せない**（王手放置・自ら利きに入る手を含む）。
- 相手の帥を取る手も例外ではない（自殺手なら指せない）。
- 判定は配置フェーズ・対局フェーズの全着手（`place`, `finishPlacement`, `move`, `capture`, `stack`, `drop`）に適用する。

### §10.2 不正な着手

§4〜§9 の条件を満たさない着手はすべて拒否され、エラーコード（§12.3）が返る。状態は変化しない。

---

## §11 終局

### §11.1 帥取り

- 相手の帥を取った側の勝ち（`reason: "marshalCaptured"`）。
- 通常は §10.1 と §11.2 により発生しないが、配置フェーズ最後の配置で王手をかけたまま対局フェーズに入り、
  相手が先に指す場合（白が対局の先手なので、黒が済を宣言済みで白が王手をかけて済、のケース）に起こり得る。

### §11.2 詰み

- 手番側に合法手が 1 つもなく、かつ帥が攻撃されている（王手）なら、手番側の負け（`reason: "checkmate"`）。

### §11.3 手詰まり

- 手番側に合法手が 1 つもなく、王手でもない場合は **引き分け**（`reason: "stalemate"`, `winner: null`）。

### §11.4 50 手ルール

- 「配置・新・取り・済宣言」のいずれも行われない手（`move` と `stack`）が **連続 51 手** 指された時点で引き分け
  （`reason: "fiftyMoveRule"`, `winner: null`）。gungi.js の `_turns_without_placing_or_capturing > 50`。
- カウンタは `place` / `drop` / `capture` / `finishPlacement` で 0 に戻る。
- 同じ着手で詰み（§11.2）も成立する場合は、**引き分けを優先** する（gungi.io サーバーの判定順）。
- 千日手（同一局面の反復）による終局はない。

⚠要チーム確認 (R-3): 50 手ルールと詰みが同時に成立した場合に引き分けを優先する点。

### §11.5 投了

- 配置フェーズ・対局フェーズのいずれでも、どちらのプレイヤーも手番に関係なく投了できる（Move `type: "resign"`）。投了した側の負け（`reason: "resignation"`）。gungi.io の forfeit に相当。

### §11.6 時間切れ・切断

- 持ち時間や切断の判定はサーバー側の責務。サーバーは Move `type: "timeout"`（負けた側を指定）をエンジンに適用して終局させる（`reason: "timeout"`）。手番に関係なく適用可。

⚠要チーム確認 (R-4): gungi.io に持ち時間はない（切断時は対局破棄）。時間切れ負けはアプリ独自の拡張。

### §11.7 合意による引き分け

- 双方の合意確認はサーバー側の責務。合意成立時、サーバーは Move `type: "agreeDraw"` を適用する（`reason: "agreement"`）。

⚠要チーム確認 (R-5): gungi.io に合意引き分けはない。アプリ独自の拡張。

### §11.8 終局後

- 終局後の状態 (`phase: "finished"`) に対する着手はすべて拒否する。

## §12 エンジン API / データ形式

### §12.1 状態 (`GameState`)

- 純粋な JSON データ（クラス・Map・Set を含まない）。WebSocket 送信・JSONB 保存にそのまま使える。
- 主なフィールド: `phase`（`placement` / `play` / `finished`）, `board`（`board[rank][file]` = 下→上の駒配列）,
  `hands`, `turn`, `placementDone`, `captured`, `ply`, `quietPlies`（§11.4 のカウンタ）, `result`。
- すべての関数は入力状態を変更しない（イミュータブル）。
- `positionKey(state)` は盤面・両者の持ち駒・手番から局面を一意に表す文字列を返す（棋譜・AI 用）。

### §12.2 着手 (`Move`)

| `type` | フェーズ | フィールド |
|---|---|---|
| `place` | placement | `player`, `kind`, `to` |
| `finishPlacement` | placement | `player` |
| `move` / `capture` / `stack` | play | `player`, `from`, `to` |
| `drop` | play | `player`, `kind`, `to` |
| `resign` | placement / play | `player` |
| `timeout` | placement / play | `player`（負けた側） |

## §15 旧仕様（公式 2023 上級編）からの主な変更

| 領域 | 旧 | 新（gungi.io） |
|---|---|---|
| 駒 | 14 種 25 枚（槍あり） | 13 種 38 枚（槍なし、大 6・中 4・小 4・兵 9・砲 2）、盤上 26 枚上限 |
| 動き | 1 段目の型を段数で一律延長 | 段ごとに個別定義（§5.3） |
| 取り・ツケの高さ条件 | 同段以下のみ | なし |
| 取り | スタック内の敵駒をすべて除外し、取った駒が移る | 最上段 1 枚のみ除外。空になったときだけ移る |
| 砦 | 制限なし | 他の駒の上に乗れない |
| 謀 | 寝返り | 擬態（真下の駒の動き） |
| 新 | 最前線まで、敵駒の上は謀のみ | 自分側 6 列、敵駒の上も可、二兵禁止 |
| 配置 | 白の済で両者終了、黒から対局 | 各自が済を宣言、白から対局、二兵禁止・砦は空マス |
| 帥取り | 自殺手でも帥取りは可 | 帥取りも自殺手なら不可 |
| 手詰まり | 手番側の負け | 引き分け |
| 千日手 | 4 回目で引き分け | なし（代わりに 50 手ルール） |
