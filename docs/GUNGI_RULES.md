# 軍儀 (Gungi) ルール仕様書 — エンジン実装準拠版

本書は `packages/gungi-engine` が **1:1 で実装する唯一の正式仕様** である。
エンジンのテスト (`packages/gungi-engine/src/*.spec.ts`) は本書のセクション番号（例: `§5.3`）を
`describe` 名に含めて対応付けている。ルールを変更する場合は **本書 → テスト → 実装** の順に更新すること。

## 準拠ルールセット

- **ルールの権威は UNIVERSAL MUSIC STORE が 2022 年に発売した HUNTER×HUNTER『軍儀』の製品ルール（以下 UMS ルール）とする。**
- UMS ルールの本文は、UMS ルールへの準拠を明記している **軍儀Web「軍儀のルール」**
  （https://gungi.2410.dev/rules.html 、2026-10-06 取得）の記述を一次資料とする。取得した記述の要点は §16 に残す。
- 同ページの図（段ごとの移動範囲図など）は取得できていない。図でしか確定しない点、および UMS ルールに記述がなくアプリ側で決めた点には
  **⚠要チーム確認** を付けた。一覧は §13。
- 以前の版（gungi.io / gungi.js 1.0.20 準拠、それ以前の公式 2023 年版準拠）はルールの根拠として **参照しない**。経緯は §15。

## §1 用語

| 用語 | 意味 |
|---|---|
| 先手 / 後手 | 先手 = 初期配置を先に始め、対局フェーズでも先に指す側（`GameState.firstPlayer`、既定は黒）。後手 = もう一方（§9.1） |
| 段 (tier) | スタック内での高さ。最下段が 1 段目。最大 3 段 |
| スタック | 1 マスに積まれた駒の列（下→上）。高さ = 駒数 |
| 最上段の駒 (top) | スタックの一番上の駒。そのマスの「持ち主」はこの駒の所有者とみなす |
| 持ち駒 (hand) | 初期配置で盤に出さなかった自分の駒。取られた駒は持ち駒にならない（§6.4） |
| ツケ | 駒を他の駒（敵味方問わず）の上に重ねること |
| 新 (あらた) | 対局フェーズで持ち駒を盤上に打つこと |
| 寝返り | 謀のツケに伴い、スタック内の敵駒をすべて同じ種類の自分の持ち駒と入れ替えること（§7） |

## §2 盤と座標

### §2.1 盤

- 9×9 = 81 マス。
- 座標は 0 始まり: `file`（筋, 0..8）, `rank`（段列, 0..8）。
- **rank 0 が黒の最奥列、rank 8 が白の最奥列**。

### §2.2 前方向

- 黒の前方 = `rank` が増える方向 (+1)。
- 白の前方 = `rank` が減る方向 (-1)。
- 駒の動きの定義（§5）は「自分から見た相対座標 (横 df, 前 dr)」で書く。白の場合は盤上で 180° 回転（df・dr とも符号反転）して適用する。

### §2.3 自陣（初期配置で置ける範囲）

- 黒の自陣 = rank 0, 1, 2
- 白の自陣 = rank 6, 7, 8

## §4 段とスタック

### §4.1 最大段数

- 1 マスのスタックは最大 **3 段**。4 段目を作る着手（ツケ・新・配置）はすべて不可。

### §4.2 動かせる駒

- 動かせるのは **各スタックの最上段の駒のみ**。下にある駒は（自分の駒でも）動かせず、利きも持たない。
- 最上段の駒が動くと、その下の駒が新たな最上段となる。

### §4.3 駒の段

- 駒の「段」= その駒がスタック内で何番目にあるか（1..3）。
- 駒の動ける範囲（§5.2）と、取り・ツケ・飛び越えの高さ条件（§5.4, §6.2）は、**移動開始時点のその駒の段** で決まる。

### §4.4 帥に関する制限

- **帥の上には、いかなる駒もツケられない**（移動・新・配置のいずれでも）。したがって帥は常に最上段にある。
- 帥自身は（§6.2 の高さ条件を満たせば）他の駒の上にツケてよい。
- 取り（§6.4）では移動先に残るのは自分の駒だけで、相手の帥は最上段にしか存在しないため、取りによってもこの不変条件は崩れない。

### §4.5 砦

- 砦に特別な制限はない。砦は他の駒と同じく、ツケ・取り・配置・新で他の駒の上に乗れ、他の駒も砦の上に乗れる（⚠ R-3）。

## §5 駒の動き

### §5.1 動きの種類

| 種類 | 定義 |
|---|---|
| 歩 (step, 範囲 n) | 指定方向へ 1..n マス進める。途中のマスに駒（敵味方・高さ問わず）があればそれより先へは進めない。駒があるマス自体へは §6 の条件で着手可 |
| 走 (slide) | 指定方向へ盤端まで何マスでも進める。途中の駒による遮断は「歩」と同じ |
| 跳 (jump) | 指定オフセットのマスへ、途中の駒を **飛び越えて** 直接着地する。飛び越えられる駒の高さに制限がある（§5.4） |

- 跳を持つのは砲・弓・筒の前方の動きだけである。それ以外の動きは、どの段でも駒を飛び越えられない。

### §5.2 段による拡張

移動開始時の駒の段を `t`（1..3）とする。

- 歩: 範囲 `n` は `n + (t − 1)` になる（2 段目で +1、3 段目で +2）。
- 走: 段の影響を受けない（大・中の無制限方向）。
- 跳: オフセット `(df, dr)` に対し、着地点は `(df, dr + k)`（`k = 0..t−1`。つまり前方へ 1 マスずつ延長）。

⚠要チーム確認 (R-1): UMS ルールの段ごとの移動範囲は図でのみ示されており、図を取得できていない。
本節の拡張規則は旧版（公式 2023 年版準拠時）の移動表を引き継いだもの。

### §5.4 飛び越えの高さ制限

#### 規則

- 跳で飛び越えるマス（下記）のどれかに、**移動する駒の段より高いスタック** があれば、その着地点へは跳べない。
  高さが駒の段以下のスタックは飛び越えられる（空マスは常に通過できる）。敵味方は問わない。
  - 例: 1 段目の弓の正面 1 マスに 2 段のスタックがあると跳べない。2 段目の弓なら跳べる。3 段目の駒はどんなスタックも飛び越えられる。
- **飛び越えるマスは、着地点の筋に関係なく、常に駒の正面の筋（同じ筋）にある。**
  着地点が `d` 段列先（`(df, d)`, `df` は −1 / 0 / +1）なら、飛び越えるマスは正面の `(0, +1) .. (0, d − 1)` の `d − 1` マス。
  - 着地点そのもののスタックの高さは §5.4 では問わない（取り・ツケの可否は §6.2 で判定する）。
  - 斜め前の `(±1, +1)` などの正面以外のマスは、どの着地点にとっても飛び越えるマスではない（高いスタックがあっても跳を妨げない）。
  - 段で延長した着地点（§5.2）は、手前の着地点のマスも飛び越える。そのため手前の着地点に高いスタックがあると、それより先の着地点へは跳べない
    （手前の着地点へは着地できる）。

## §6 盤上の着手（移動・取り・ツケ）

### §6.1 着手の種類

手番側は自分の最上段の駒を 1 つ選び、§5 で到達可能なマス（移動先）に対して次のいずれかを行う。

| 種類 | Move `type` | 移動先の条件 |
|---|---|---|
| 移動 | `move` | 移動先が空 |
| 取り | `capture` | 移動先の最上段が **敵の駒**、かつ §6.2 の高さ条件 |
| ツケ | `stack` | 移動先にスタックがある（最上段は敵味方どちらでもよい）、かつ §6.2・§6.3 |

最上段が敵の駒であるマスに対しては、「取り」と「ツケ」の両方が選択肢になり得る。どちらを行うかは Move で明示する。

### §6.2 高さ条件（移動先が自分の段以下）

- 移動する駒の段を `t`、移動先スタックの高さを `h` とすると、**`h ≤ t` のときだけ** 取り・ツケができる。
  - 1 段目の駒は高さ 2 のスタックを取ることもツケることもできない。2 段目の駒は高さ 2 のスタックにツケられる。
    高い段から低いスタックへは常に条件を満たす。

### §6.3 ツケの追加条件

- 移動先の高さ `h < 3`（§4.1）。ツケた駒の段は `h + 1` になる。
- 移動先の最上段が帥でない（§4.4）。

### §6.4 取りの処理

- 取れるのは移動先の **最上段が敵の駒** の場合だけ。最上段が自分の駒なら、その下に敵の駒があっても取れない（ツケのみ可）。
- 移動先スタック内の **敵の駒はすべて** 取られる（最上段だけではない）。
- 同スタック内の **自分の駒は残り**、元の順序のまま下に詰める。動いた駒はその上に乗る。
- 取られた駒はゲームから除外される（持ち駒にはならない）。取った側の `captured` 記録に残す。

例: 下から [白兵, 黒侍, 白槍] のスタックを黒（3 段目の駒）が取ると、白兵と白槍が除外され [黒侍, 黒(移動した駒)] になる。

## §7 寝返り（謀）

### §7.1 発生条件

- 謀が **ツケ（§6.1 の `stack`）** で乗ったスタックに **敵の駒が 1 枚以上ある** とき、寝返りを行うことができる（任意）。
- 敵の駒はスタック内のどこにあってもよい。**最上段が自分の駒で、その下に敵の駒がある場合も** 寝返りできる（取りとの違い）。
- 謀の `move`・`capture` では発生しない。新（§8）で謀を打った場合も発生しない（⚠ R-4）。
- 相手の帥は常に最上段にあり、帥の上にはツケられない（§4.4）ので、帥が寝返ることはない。

### §7.2 処理

- スタック内の **敵の駒すべて** を、**同じ種類の自分の持ち駒** と入れ替える（一部だけの寝返りはできない）。
  - 入れ替えに必要な枚数（種類ごとの敵駒の枚数）がすべて持ち駒にある場合だけ寝返りできる。1 種類でも足りなければ寝返りはできない（ツケのみ可）。
- 入れ替えた持ち駒は、敵の駒があった位置にそのまま入る（スタックの順序は変わらない）。持ち駒はその分だけ減る。
- 入れ替えられた敵の駒はゲームから除外され、取った駒と同様に寝返らせた側の `captured` 記録に残す。

例: 黒の謀（1 段目）が [白兵, 黒侍] にツケて寝返りを行う（黒の持ち駒に兵が 1 枚以上ある）と、[黒兵, 黒侍, 黒謀] になり、
黒の持ち駒の兵が 1 枚減り、白兵は除外される。

### §7.3 指定方法

- `stack` の Move に `betray: true` を付けると寝返りを行う。省略または `false` なら寝返りなしのツケ。
- 寝返りできないツケ（謀でない・敵駒がない）や `stack` 以外の着手に `betray: true` を付けた場合は `INVALID_BETRAYAL`、
  持ち駒が足りない場合は `BETRAYAL_HAND_SHORT` で拒否する。
- `legalMoves` は、寝返り可能なツケについて「寝返りなし」と「`betray: true`」の 2 つの手を列挙する。

## §8 新（持ち駒を打つ）

### §8.1 基本

- 対局フェーズで、手番側は着手の代わりに持ち駒を 1 枚盤上に打てる（Move `type: "drop"`）。1 手として数える。

### §8.2 打てる段列（最前線ルール）

- 自分の最奥列から、**最上段が自分の駒であるスタックがある最も前方の段列（最前線）** までの範囲にのみ打てる。
  - 例: 黒の駒の最前線が rank 2 なら rank 0..2、rank 4 なら rank 0..4 に打てる。
- 最前線の判定に使うのは **各スタックの最上段の駒だけ** である（R-5、公式の図で解決済み）。
  - 敵の駒の下に埋もれた自分の駒は最前線を進めない。例: 黒兵の上に白侍が乗った [黒兵, 白侍] が rank 6 にあっても、黒の最前線は rank 6 にならない。
  - 敵の駒の上に自分の駒が乗ったスタック（最上段が自分）は最前線に数える。例: [白兵, 黒兵] が rank 6 にあれば黒の最前線は rank 6 以上。
- 対局フェーズでは帥が常に最上段にあるので（§4.4）、最前線は必ず存在する。
- 回帰テスト: `drops.spec.ts` の `§8.2 front line`（黒・白の両方）。

### §8.3 打てるマス

- 空マス、または
- 最上段が **自分の駒** で高さ `< 3`、かつ最上段が帥でないスタック（新でのツケ）。
- 最上段が **敵の駒** のスタックには打てない（`OCCUPIED_BY_ENEMY`）。
- 新では取りも寝返りも発生しない。§6.2 の高さ条件は新には適用しない（打った駒の段は打った後の高さになる）。

### §8.4 その他

- 二歩・打ち歩詰めなど将棋の制限はない。

## §9 初期配置フェーズ（自由配置）

### §9.1 開始状態と先手の決定

- 盤は空。両者とも 25 枚すべてが持ち駒。手番は **先手**。
- 先手は `createInitialState({ firstPlayer })` で指定する（`'black'` / `'white'`、省略時は `'black'`）。`GameState.firstPlayer` に記録される。
- 公式の対面プレイでは、両者が帥を盤の中央へ向けて落とし、中央に近い方が先手になる（帥落とし）。エンジンは物理的な判定を行わない。
  **帥落としはサーバー／UI 層が再現し（ランダム決定や演出付きのアニメーションなど）、その結果を `firstPlayer` として渡す**（⚠ R-6）。
- 自陣（§2.3）と前方向（§2.2）は色で決まり、先手かどうかには依存しない。

### §9.2 配置手 (`place`)

- 手番側は持ち駒を 1 枚、**自陣（§2.3）** のマスに置く。
- 置けるマス: 空マス、または最上段が自分の駒で高さ `< 3`、最上段が帥でないスタック（自陣内でのツケ）。
- **各プレイヤーの最初の配置は帥でなければならない。**

### §9.3 配置完了 (`finishPlacement`)

- 手番側は配置の代わりに「済」を宣言できる。帥を置いていなければ宣言できない。
- **先手が済** → 先手の配置は終了。以後、後手が単独で配置を続ける。
- **後手が済** → その時点で **両者の配置フェーズが終了** する（先手が済を宣言していなくても）。
- 持ち駒をすべて置いたプレイヤーは、その配置の時点で済を宣言したものとみなす（後手なら配置フェーズが終了する。⚠ R-7）。
- 配置しなかった駒は持ち駒として残り、対局中に新で使える。

### §9.4 手番の進行

- 両者とも未完了の間は交互に配置する（先手から）。
- 先手が完了済みなら、後手が連続して配置する。
- 配置フェーズが終了すると対局フェーズに移行し、**先手から** 指す（⚠ R-6）。

### §9.5 配置フェーズ中の王手

- 配置した駒の利きで相手の帥が攻撃されることがある（王手）。§10.1 の自殺手禁止は配置フェーズにも適用する:
  - 自分の帥が攻撃されたままになる配置・済宣言はできない。
  - 王手をかけられた側は、利きを遮る配置で解消しなければならない。解消できなければ詰み（§11.2）。
- 先手が済を宣言した後は、後手の配置で先手が王手をかけられても先手は応じられない。その場合、先手は王手をかけられた状態で対局フェーズの最初の手番を迎える（§9.6）。
- 後手は自分が王手をかけられたまま配置を終えられないので、対局開始時に後手が王手をかけられていることはない。

### §9.6 即死筋（早すぎる済）

- 先手が早く済を宣言すると、後手は単独で配置を続けて先手の帥を狙う駒組み（大の筋・砲の跳・中の斜めなど）を完成させられる。
  後手が済を宣言して対局が始まった時点で、先手は王手をかけられており、逃げ道がなければ **対局開始と同時に詰み**（§11.2）になる。
- これは公式の対局で知られた筋であり、**仕様どおりの挙動である**（禁止も救済もしない）。上級者は配置の序盤（3 手目前後）から帥の守りを置いて、
  4 手目以降の配置で即死する筋を防ぐ。先手が済を宣言していなければ、王手には配置で応じなければならない（§9.5）。
- 対局フェーズは先手から指すため、この筋は「先手が帥を取られる」形ではなく「先手が詰んで始まる」形で現れる（§11.1）。
- エンジンはこの終局を後手の済（またはその最後の配置）を適用した時点で判定するため、状態は **`placement` から `play` を経ずに直接 `finished`**
  になる（`reason: "checkmate"`。合法手がなく王手でもなければ `"stalemate"`）。§9.5 の配置中の詰みも同様。
  **クライアントは `play` フェーズが必ず現れると仮定してはならない**（対局開始の演出・通知などは `phase` の遷移を見て分岐する）。
- アプリは将来、早すぎる済に対する **任意の UI 警告** を追加してよい。ただしそれは UI の機能であり、エンジンのルールではない。
- 回帰テスト: `engine.spec.ts` の `§9.6 sudden death after an early finish (即死筋)`（黒先手・白先手の両方）。

## §10 禁じ手

### §10.1 自殺手（帥を取られる状態にする手）

- 着手後、**相手の次の 1 手で自分の帥が取られ得る状態になる手は指せない**（王手放置・自ら帥を取られる位置に動く手を含む）。
- 「帥が取られ得る」= 相手のいずれかの最上段の駒が、§5（飛び越えの高さ制限を含む）で帥のマスに到達でき、
  かつ §6.2 の高さ条件（駒の段 ≥ 帥のいるスタックの高さ）を満たす。
- 相手の帥を取る手も例外ではない（そもそも §10.1 により相手の帥が取られ得る局面は生じない。§11.1）。
- 判定は配置フェーズ・対局フェーズの全着手（`place`, `finishPlacement`, `move`, `capture`, `stack`, `drop`）に適用し、
  着手後の局面は実際に適用する処理（取り §6.4・寝返り §7.2 を含む）で求める。

⚠要チーム確認 (R-8): UMS ルールは「帥の捕獲が回避できない場合は詰み」とだけ述べ、自殺手の扱いを明記していない。
アプリでは帥を取られる手を **受け付けない（エラーを返す）** 方式とし、詰み（§11.2）をそのまま判定する。配置フェーズにも適用する（§9.5）。

### §10.2 不正な着手

§4〜§9 の条件を満たさない着手はすべて拒否され、エラーコード（§12.3）が返る。状態は変化しない。

## §11 終局

### §11.1 帥取り

- UMS ルールの「相手の帥を先に捕獲した方が勝ち」は、**§11.2 の詰み判定として実装済み** である。帥の捕獲が回避できない局面は、
  帥を実際に取る手を待たずに、その局面を作った手の適用時点で詰み（`reason: "checkmate"`）として終局する。
- §10.1 により、合法な対局では相手の帥が取れる局面は生じない（`createPosition` / `stateError` もそのような局面を拒否する。§12.1）。
  §9.6 の即死筋も、先手が詰んだ状態で対局が始まる形になり、帥取りは起きない。
- 帥取りの終局（`reason: "marshalCaptured"`、取った側の勝ち）は、壊れた状態や不正に取り込まれた状態に対する **防御的な経路** としてのみ残している。
  合法な対局でこの結果が返ることはない（回帰テスト: `engine.spec.ts` の `§11.1 marshal capture`）。
- 合法な対局は必ず次のいずれかで終わる: 詰み（§11.2）・手詰まり（§11.3）・千日手（§11.4）・投了（§11.5）・時間切れ（§11.6）・合意引き分け（§11.7）。

### §11.2 詰み

- 手番側に合法手が 1 つもなく、かつ帥が攻撃されている（王手）なら、手番側の負け（`reason: "checkmate"`）。
- 判定は `applyMove` が配置フェーズ・対局フェーズの **すべての着手の適用後** に行う（配置フェーズの終了で対局フェーズへ移る着手を含む）。
  詰み・手詰まりは千日手より先に判定する。終局した状態は `phase: "finished"` になり、`isGameOver` が真を返す。
- 例外は `createPosition` で直接作った局面だけで、詰みの局面でも終局として返さない（§12.1。`legalMoves` と `inCheck` で呼び出し側が判定する）。
- 回帰テスト（`engine.spec.ts`）:
  - `§11.2 checkmate` — 詰ます手の適用で終局する、新での合い駒（最前線までなら防げる／最前線より先には打てない）、新による詰み。
  - `§9.5 check during placement` — 自陣内で遮れない配置中の王手は詰み。
  - `§9.6 sudden death after an early finish (即死筋)` — 配置フェーズから直接詰みで終局する（黒先手・白先手）。
  - `random self-play invariants` — 未終局の状態には必ず合法手があり（詰みの見逃しがない）、終局した状態には合法手がない。
  - `§12 legalMoves is exactly the set of moves validateMove accepts` — 詰みの判定に使う合法手の列挙が、受け付ける手と完全に一致する。
  - 王手の検出そのものは `rules.spec.ts` の `§10.1 check detection`、自殺手の拒否は `engine.spec.ts` の `§10.1 self-check is rejected`。

### §11.3 手詰まり

- 手番側に合法手が 1 つもなく、王手でもない場合は **引き分け**（`reason: "stalemate"`, `winner: null`）。

⚠要チーム確認 (R-9): UMS ルールに手詰まりの規定はない。

### §11.4 千日手

- 対局フェーズで **同一局面（盤面・両者の持ち駒・手番がすべて一致）が 4 回目に現れた時点で対局終了**
  （`reason: "fourfoldRepetition"`, `winner: null`）。
- 対局フェーズ開始時の局面を 1 回目として数える。
- 取り・新・寝返りの後に、それ以前の局面が再び現れることはない（駒は盤上と持ち駒から減る一方で、持ち駒は増えない）。
  したがって数え直しはこれらの手（不可逆手）で 0 から始める（§12.1 `positionCounts`）。
- 同じ着手で詰み・手詰まりも成立することはない（同一局面が以前に現れ、その局面で対局が続いている以上、合法手がある）。

#### 他のルールとの比較

| ルール | 成立条件 | 扱い |
|---|---|---|
| 将棋 | 同一局面 4 回目 | 無勝負。先後を入れ替えて指し直し |
| チェス | 同一局面 3 回目 | 引き分けを請求できる（自動終局ではない。5 回目で自動引き分け） |
| 軍儀 (UMS) | 同一局面 4 回目 | 再勝負 |

#### エンジンとアプリの役割分担

- **エンジン** は UMS の回数（4 回目）を採用し、その時点で対局を **終局** として返す
  （`phase: "finished"`, `result: { winner: null, reason: "fourfoldRepetition" }`）。請求の手順はなく、自動で終局する。
  エンジンは新しい対局を自動で始めない。
- **アプリ** は UMS の「再勝負」を、将棋の指し直しと同じく **先後を入れ替えた再戦** として実現する。
  前局の `firstPlayer` の反対側を先手にして `createInitialState({ firstPlayer })` で新しい対局を作る（§9.1。エンジン側の追加実装は不要）。
  再戦の開始方法（自動開始・両者の承認）、前局と再戦の関係付け、レーティングや戦績での扱い（前局は無勝負とする等）はサーバー／アプリ側で決める。
- 回帰テスト: `engine.spec.ts` の `§11.4 fourfold repetition`。

⚠要チーム確認 (R-10): 上記のとおり、エンジンは 4 回目で勝者なしの終局、アプリは先後を入れ替えた再勝負とする。
チームが再勝負を不要と判断した場合の代替は、`fourfoldRepetition` を **通常の引き分け** として記録するだけでよい（エンジンの変更は不要）。

### §11.5 投了

- 配置フェーズ・対局フェーズのいずれでも、どちらのプレイヤーも手番に関係なく投了できる（Move `type: "resign"`）。投了した側の負け（`reason: "resignation"`）。

### §11.6 時間切れ・切断

- 持ち時間や切断の判定はサーバー側の責務。サーバーは Move `type: "timeout"`（負けた側を指定）をエンジンに適用して終局させる（`reason: "timeout"`）。手番に関係なく適用可。
- **エンジンだけでは終わらない対局がありうる**。UMS ルールには駒不足による引き分けも手数上限もなく、エンジンも追加しない。
  たとえば帥だけが残った局面で両者が同一局面を 4 回繰り返さないように指し続ければ、§11.2〜§11.4 のどれも成立しない。
  **対局の長さを有限に抑えるのはアプリの責務** であり、持ち時間（時間切れ）や無操作タイムアウトで必ず終局させること。

### §11.7 合意による引き分け

- 双方の合意確認はサーバー側の責務。合意成立時、サーバーは Move `type: "agreeDraw"` を適用する（`reason: "agreement"`）。

⚠要チーム確認 (R-11): 時間切れ負け・合意引き分けは UMS ルールにないアプリ独自の拡張。

### §11.8 終局後

- 終局後の状態 (`phase: "finished"`) に対する着手はすべて拒否する。

## §12 エンジン API / データ形式

### §12.1 状態 (`GameState`)

- 純粋な JSON データ（クラス・Map・Set を含まない）。WebSocket 送信・JSONB 保存にそのまま使える。
- 主なフィールド: `phase`（`placement` / `play` / `finished`。`placement` から直接 `finished` になることがある。§9.6）, `board`（`board[rank][file]` = 下→上の駒配列）,
  `hands`, `turn`, `firstPlayer`（§9.1）, `placementDone`, `captured`, `ply`, `positionCounts`, `result`。
- すべての関数は入力状態を変更しない（イミュータブル）。
- `createInitialState({ firstPlayer })` は `firstPlayer` が `'black'` / `'white'`（または省略）以外なら `RangeError` を投げる（プログラムエラー扱い。サーバーは入力を検証してから渡す）。
- `positionKey(state)` は盤面・両者の持ち駒・手番から局面を一意に表す文字列（約 140 文字）を返す。人が読める形式で、棋譜・解析・AI 用。
- `positionHash(state)` は `positionKey` の UTF-8 バイト列の 64 ビット FNV-1a ハッシュを 16 桁の小文字 16 進文字列で返す（`POSITION_HASH_LENGTH`）。§11.4 の千日手判定に使う。
  衝突すると別局面を同一局面と数えうるが、数え直し区間の局面数 n は高々数百で、衝突確率は誕生日問題の上界 n²/2⁶⁵
  （n = 300 で約 2.4×10⁻¹⁵、n = 10,000 でも約 2.7×10⁻¹²）なので無視できる。
- `positionCounts` は、対局フェーズ開始または直近の不可逆手（`capture`、`drop`、`betray: true` の `stack`）以降に現れた
  各局面の `positionHash` とその出現回数（現在の局面を含む）。配置フェーズ中は空（`{}`）。
  キーを `positionKey` ではなくハッシュにするのは、長い対局で履歴が状態の大半を占めるのを防ぐため
  （300 手・296 局面の対局で状態全体が約 45 KB → 約 7 KB）。
- `createPosition(setup)` は任意局面（テスト・AI・棋譜読み込み）から対局フェーズの状態を作る（`setup` は `stacks`, `hands`, `turn`, `firstPlayer`。
  `firstPlayer` は省略時 `'black'` で、対局フェーズのルールには影響しない）。
  与えた局面を §11.4 の 1 回目として数える。
  到達し得ない局面を作らないよう、次の不変条件を検査し、違反時は `InvalidPositionError`（`reason` にコード）を投げる。
  これらは合法な対局が常に保つ **必要条件** であり、通過しても実際にその局面へ至る手順が存在するとは限らない。
  投げずに検査したい場合は `positionError(setup)` が理由コードまたは `null` を返す。
  `positionError` は任意の JSON 値に対して例外を投げない（構造が壊れた入力にもコードを返す）。
  - `setup` がオブジェクトで、`stacks` が配列、その各要素と `hands`・`hands.black`/`hands.white` がオブジェクト（`MALFORMED`）
  - マス座標が盤内で重複しない／駒の種類・所有者が正しい（`INVALID_SQUARE`, `DUPLICATE_SQUARE`, `INVALID_PIECE`）
  - スタックの高さ ≤ 3（`STACK_TOO_HIGH`、§4.1）
  - 帥は各陣営ちょうど 1 枚（`MARSHAL_COUNT`）で、スタックの最上段にある（`MARSHAL_NOT_ON_TOP`、§4.4）
  - 盤上＋持ち駒が駒種ごとに §3.1 の枚数以下（`ROSTER_EXCEEDED`）
  - 持ち駒が 0 以上の整数（`INVALID_COUNT`）
  - 手番・`firstPlayer` が `black` / `white`（`INVALID_TURN`）
  - 手番でない側の帥が攻撃されていない（`OPPONENT_IN_CHECK`、§10.1）。例外はない:
    対局フェーズは先手の手番で始まり、後手は王手をかけられたまま配置を終えられない（§9.5）ため、
    先手が黒でも白でも、対局フェーズで手番でない側が王手をかけられている局面は存在しない
    （§9.6 の即死筋で対局開始時に王手をかけられているのは、手番側の先手である）
  - 検査しないもの（受け入れたまま返す）:
    - 詰み・手詰まりの局面。`result: null`・`phase: "play"` のまま返す（終局判定は着手の適用時にしか行わない）。
      呼び出し側が判定する: `legalMoves(state).length === 0` なら終局で、`inCheck(state)` が真なら詰み（§11.2）、偽なら手詰まり（§11.3）。
      `isGameOver` は `phase` を見るだけなので、この局面では `false` を返す
    - 配置・着手の経緯に依存する条件（各駒が自陣内にあるか等）。`createPosition` は手順を持たないため
- `stateError(state)` は `GameState` 全体を検査し、理由コードまたは `null` を返す（任意の JSON 値に対して例外を投げない）。
  **DB・WebSocket などから復元した状態をエンジンに渡す前の関門として、これを呼ぶことを推奨する**（壊れた状態は下記のとおり例外の原因になる）。
  - 全フィールドの構造（`board` が 9×9 の駒配列、`hands` が全駒種の個数、`placementDone` が真偽値、`captured` が駒種の配列、
    `ply` が 0 以上の整数、`positionCounts` が文字列 → 1 以上の整数のオブジェクト）（`MALFORMED`, `INVALID_PIECE`, `INVALID_COUNT`, `INVALID_TURN`）
  - `phase` が既知の値で `placementDone` と矛盾しない（`INVALID_PHASE`）:
    `play` なら両者済。`placement` なら後手は未済（後手の済で配置フェーズは終わる）、持ち駒が 0 の側は済（§9.3）
  - 配置フェーズの手番（`INVALID_TURN`、§9.4）: 手番が済の側にない。両者とも未済なら、すべての手が先手から交互の `place` なので、
    盤上の駒数は先手の手番なら両者同数、後手の手番なら先手が 1 枚多い。先手が黒でも白でも同じ規則で検査する
  - `result` は `finished` のときだけ存在し、`reason` が §11 の値で、引き分けの理由なら `winner: null`、それ以外は勝者がいる（`INVALID_RESULT`）
  - `positionCounts` がフェーズと現在の局面に合う（`INVALID_HISTORY`）: キーはすべて `positionHash` の形式（16 桁の小文字 16 進）。配置フェーズでは空。
    対局フェーズでは現在の局面が 1..3 回、他の局面も 1..3 回。終局後は 1..3 回で、ただし `fourfoldRepetition` の終局では現在の局面がちょうど 4 回
  - `positionError` と同じ盤面の不変条件（`STACK_TOO_HIGH`, `MARSHAL_NOT_ON_TOP`）
  - フェーズに応じた駒数: 帥は各陣営 1 枚以下で、対局フェーズでは必ず 1 枚、配置フェーズでは駒を置いた・済を宣言した側は 1 枚（§9.2）。
    盤上＋持ち駒＋相手に取られた駒（寝返りで除外された駒を含む）が駒種ごとに §3.1 の枚数以下（`MARSHAL_COUNT`, `ROSTER_EXCEEDED`）
  - 手番でない側の帥が攻撃されていない（`OPPONENT_IN_CHECK`）。例外は配置フェーズで手番でない側（済を宣言した先手）の場合だけ（§9.5, §9.6）。終局後は検査しない
  - `positionError` と同じく、未判定の詰み・手詰まりは受け入れ、手順の再現（棋譜の検証）は行わない
- `applyMove` / `validateMove` / `legalMoves` などは、上記の不変条件を満たす状態（`createInitialState` / `createPosition` / `applyMove`
  が返したもの）を前提とする。壊れた状態ではプログラムエラーとして例外を投げることがある（着手 `Move` は不正でも例外にならず §12.3 のコードを返す）。

### §12.2 着手 (`Move`)

| `type` | フェーズ | フィールド |
|---|---|---|
| `place` | placement | `player`, `kind`, `to` |
| `finishPlacement` | placement | `player` |
| `move` / `capture` | play | `player`, `from`, `to` |
| `stack` | play | `player`, `from`, `to`, `betray?`（§7.3） |
| `drop` | play | `player`, `kind`, `to` |
| `resign` | placement / play | `player` |
| `timeout` | placement / play | `player`（負けた側） |
| `agreeDraw` | placement / play | なし |

- `betray` は省略・`true`・`false` のいずれか。それ以外の値は `INVALID_MOVE`。

| コード | 意味 |

| `GAME_FINISHED` | 終局後の着手 |

## §16 原典の要点（軍儀Web「軍儀のルール」2026-10-06 取得時点）

本書の根拠とした記述の要点を、取得時点の内容に沿って記録する（文言は要約）。

- 基本: 9×9 盤、各 25 枚。相手の帥を先に捕獲した方の勝ち。
- 駒: §3.1 の 14 種・枚数。1 段目の動きは §5.3 の表のとおり（帥=玉、大=竜、中=竜馬、小=金、槍=侍より前へ 1 マス多い、
  砦=「大」の字、砲・筒・弓は前方の跳）。
- 段: ツケで段が上がると移動範囲が広がる（図あり・未取得）。大・中の無制限方向は段の影響を受けない。
  砲・弓・筒の前方の跳以外は、どの段でも駒を飛び越えられない。
- 初期配置: 任意のプレイヤーを先手とし（公式の対面プレイでは帥落としで決める）、帥から交互に 1 枚ずつ自陣 3 段列に置く。3 段までツケ可、帥の上は不可。
  持ち駒を残して終える場合は「済み」を宣言する。先手が済んでも後手は続けられ、後手が済んだ時点で（先手が済んでいなくても）配置は終わる。
  残した駒は手駒として使える。
- 手番: 動かす・ツケ・取る・新のいずれか 1 つ。
- ツケ: 移動範囲内の駒（敵味方問わず）の上に重ねられる。3 段まで、帥の上は不可。動かす駒の段が移動先の高さ以上であること。
- 取る: 移動範囲内の敵駒を取れ、取った駒は対局終了まで使わない。高さ条件はツケと同じ。移動先の最上段が敵駒であること
  （自駒の下の敵駒は取れず、ツケのみ可）。移動先の敵駒はすべて取る。
- 新: 配置しなかった駒を、盤上の自駒の最前線と同じかそれより手前の段列に置ける。自駒の上には可、敵駒の上には不可。
- 飛び越え: 砲・筒・弓は前方（弓は前方 3 方向）で駒を飛び越えられる。自分の段より高い駒は飛び越えられない。
- 寝返り: 謀がツケたマスに敵駒があれば、手駒の同種の駒と入れ替えられる（任意）。同種がなければ不可。
  敵駒が複数なら全部を入れ替える必要がある。最上段が自駒でも可。入れ替えた敵駒は取った駒と同様に盤外へ。
- 終了: 帥の捕獲で勝ち。捕獲が回避できなければ詰み。投了も可。
- 千日手: 同一局面が 4 回現れたら再勝負（軍儀Web 自体は 2025 年 1 月時点で未実装）。
