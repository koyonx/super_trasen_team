# 軍儀 (Gungi) Online — プロジェクト概要ドキュメント

ft_transcendence (subject Version 21.2) を題材に、オンライン対戦ボードゲーム「軍儀」を構築する。
本ドキュメントは課題仕様の要約、採用モジュール（チーム決定済み・準必須扱い）、アーキテクチャ、インフラ構成、技術スタックをまとめたもの。

## 1. 課題仕様の要約 (subject v21.2)

### 1.1 プロジェクトの性質

- 4〜5人のグループプロジェクト。テーマは自由（Pong固定ではない）。
- **必須パート（全員が貢献）+ モジュール選択で合計14ポイント以上**を獲得する。
  - Major モジュール = 2pt / Minor モジュール = 1pt
  - 評価で動かないモジュールは0pt。
  - ボーナス: 14pt超過分は最大5ptまで加点。
- 本チームは14ptを大きく超える構成（§3参照、準必須21pt。2026-10-06 に 43pt → 24pt、2026-10-07 に 24pt → 21pt と2段階で縮小）を目指す。

### 1.2 チーム体制（README に明記必須）

| ロール | 責務 |
|---|---|
| Product Owner (PO) | プロダクトビジョン、バックログ管理、優先度決定、完了検収 |
| PM / Scrum Master | 会議運営、進捗・期限管理、リスク・ブロッカー管理 |
| Tech Lead / Architect | アーキテクチャ・技術選定、コード品質、重要変更のレビュー |
| Developers（全員） | 機能実装、コードレビュー参加、テスト、ドキュメント |

評価では「役割分担・作業分担・コミュニケーション方法・各人の貢献」の説明が求められる。

### 1.3 必須要件（違反すると rejected）

- **Web アプリであること**: frontend + backend + database の3層必須。
- **Git**: 全メンバーのコミット、明確なコミットメッセージ、適切な作業分担が履歴に見えること。
- **コンテナ**: Docker 等でデプロイし、**1コマンドで起動**できること。
- 最新安定版 **Google Chrome** で動作。ブラウザコンソールに **JS の warning / error を出さない**。
- **Privacy Policy と Terms of Service ページ必須**（フッター等からアクセス可能、中身のあるもの。プレースホルダは rejected）。
- **マルチユーザー同時利用必須**: 複数ユーザーの同時ログイン・同時操作、リアルタイム反映、レースコンディションやデータ破壊がないこと。

### 1.4 技術要件（必須）

- レスポンシブでアクセシブルなフロントエンド。
- **CSS フレームワーク / スタイリングソリューション**を使用。
- 資格情報は `.env`（Git 管理外）+ `.env.example` を提供。
- DB は**明確なスキーマとリレーション**を持つこと。
- **ユーザー管理**: 最低限 email + password 認証（ハッシュ + ソルト）。OAuth / 2FA はモジュール扱い。
- **全フォーム・入力のバリデーションをフロント/バック両方**で行う。
- ブラウザ・外部からバックエンドへの接続はすべて **HTTPS**（コンテナ内部の通信は平文可）。

### 1.5 README 要件（評価対象）

- 冒頭1行目（イタリック）: *This project has been created as part of the 42 curriculum by \<login1\>, ...*
- 必須セクション: Description / Instructions（前提・.env 設定・起動手順）/ Resources（参考資料 + **AI をどのタスク・どの部分に使ったかの説明**）

- **その場での小規模なコード修正**を求められる場合があるため、全員がコードを説明・変更できる状態にしておく。

## 2. ゲーム: 軍儀 (Gungi)

9×9盤の将棋類似ボードゲーム。駒を最大3段まで「ツケ」で積み重ねられるのが特徴。
帥（すい）を取ったら勝ち。初期配置フェーズ（自由配置）と対局フェーズがある。

- 明確なルールと勝敗条件を README / アプリ内に明記（Major「web-based game」の要件）。
- ライブ対戦（リアルタイムマルチプレイヤー）。
- 描画は 2D で開始。**3D化（Three.js等）は検討枠**（§3.2）。

サーバー権威 (server-authoritative) モデルで実装する:
盤面状態・合法手判定・勝敗判定はすべてバックエンドが持ち、クライアントは表示と入力のみ。
→ チート防止と「レースコンディションなし」要件を同時に満たす。

### 3.3 SSR vs ICP の結論: **SSR を採用、ICP は不採用**

subject の制約で両者は排他。以下の理由で SSR を推奨し、こちらで確定とする（異議があればチームで再協議）:

1. 本構成のバックエンドは WebSocket 常時接続・PostgreSQL・GraphQL が中核。ICP はバックエンドをブロックチェーン上の canister で動かす前提であり、**この構成のほぼ全てと衝突**する（Postgres も WebSocket サーバーも通常の形では載らない）。
2. ICP (1pt) のためだけに上記の構成を崩す価値はない（縮小後の構成はブロックチェーン系モジュールを採用していない）。
3. SSR (1pt) は FE フレームワークのメタフレームワーク（Next.js 等）を選べばほぼ標準機能で満たせる。

### 3.4 依存関係チェック（全て充足）

- ゲーム前提モジュール（AI対戦・カスタマイズ）→ 軍儀本体を採用済み ✓
- ユーザー活動分析・高度な権限 → 標準ユーザー管理を採用済み ✓
- SSR → ICP 不採用により競合なし ✓
- ゲームカスタマイズ採用により、**AI はカスタマイズ設定にも対応する必要あり**（subject 明記）
- 縮小で外したモジュールに依存する採用モジュールはない（依存の連鎖は §3.5）✓

## 4. 技術スタック

### 4.1 確定事項

| 項目 | 決定 |
|---|---|
| データベース | **PostgreSQL**（確定） |
| API | **GraphQL**（確定）— アプリ内 FE⇔BE 通信の主軸 |
| リポジトリ構成 | **モノレポ、`server/` と `client/` をディレクトリ分割**（確定） |
| コンテナ | Docker / Docker Compose（subject 必須） |

### 4.2 言語・フレームワーク（決定: TypeScript 統一 = 構成A）

| レイヤ | 決定 |
|---|---|
| client | **Next.js**（React、SSR モジュール要件を App Router の SSR で満たす）+ Tailwind CSS |
| server | **NestJS + GraphQL (Apollo, code-first)** + Socket.IO |
| ORM | **Prisma**（マイグレーション含む。ORM Minor 申請候補） |
| 共有 | npm workspaces の `packages/gungi-engine`（ルールエンジン）と `packages/shared`（型・Zod スキーマ・棋譜形式）を FE/BE/AI で共有 |

TS 統一の利点: 型・バリデーション・ゲームエンジンの単一ソース化。エンジンは server（権威判定）・client（事前検証/表示）・AI（探索）の3箇所から再利用する。

### 4.3 API 層: GraphQL のみ

自アプリの FE⇔BE 通信はすべて **GraphQL**（クエリ・ミューテーション・サブスクリプション）で行う。
公開 API モジュールは縮小でスコープ外（§3.5）としたため、REST `/api/v1` 層・APIキー・レート制限・OpenAPI は作らない。

### 4.4 その他の構成要素

| レイヤ | 方針 |
|---|---|
| スタイリング | CSS フレームワーク必須要件。Tailwind CSS を第一候補（言語決定に依存しない） |
| リアルタイム | WebSocket（GraphQL Subscriptions または Socket.IO 系。BE言語決定後に確定） |
| 認証 | email+password（argon2/bcrypt ハッシュ+ソルト）+ OAuth 2.0 + JWT (httpOnly cookie) |
| バリデーション | FE/BE 両側必須。スキーマ定義（GraphQL スキーマ + 入力バリデータ）を単一ソース化 |
| アバター保存 | server コンテナのボリュームに保存（チャットメディア・棋譜ファイルがなくなったため MinIO は不採用） |

## 5. リポジトリ構成（モノレポ）

```
/
├── client/                  # フロントエンド（SSR 対応フレームワーク）
│   ├── src/
│   └── Dockerfile
├── server/                  # バックエンド（GraphQL + WebSocket）
│   ├── src/
│   └── Dockerfile
├── packages/                # 共有パッケージ（言語構成Aの場合）
│   ├── gungi-engine/        # 軍儀ルールエンジン（盤面・合法手・勝敗判定）
│   └── shared/              # 型・バリデーションスキーマ・棋譜フォーマット定義
├── infra/
│   ├── docker-compose.yml   # 1コマンド起動（必須要件）
│   └── nginx/               # TLS終端・リバースプロキシ
├── docs/
├── .env.example
└── README.md
```

※ BE を TypeScript 以外にする場合、`gungi-engine` は server 内実装となり `packages/` は FE 用共有のみになる。

## 7. インフラ構成

- **`docker compose up --build` の1コマンドで全サービス起動**（必須要件）。
  - コンテナ: `nginx` / `client`(SSRサーバー) / `server` / `postgres`
- **HTTPS**: nginx で終端（自己署名 or mkcert）。コンテナ内部は平文可（subject 明記）。
- **環境変数**: `.env`（gitignore）+ `.env.example`。DB接続、JWT、OAuthクライアント等。
- **CI（推奨）**: lint / typecheck / エンジン unit test / E2E スモーク（コンソールエラー検出込み）/ `docker compose build`。
