## 1. Product Owner (PO)

**ミッション**: 「何を作るか」の最終責任者。プロダクトの価値と評価での得点を最大化する。

### subject が求める責務
- プロダクトビジョンの定義と機能の優先順位付け
- プロダクトバックログの維持管理
- 機能と優先度に関する意思決定
- 完了した作業の検収（バリデーション）
- ステークホルダー（評価者・ピア）とのコミュニケーション

### 本プロジェクトでの具体的な仕事
- **モジュール43ptの進捗と完成度の管理**: 「動かないモジュール=0pt」なので、中途半端なモジュールを増やすより完成済みを積み上げる判断を下す。フェーズ末 DoD（[TASKS.md](./TASKS.md)）の検収者。
- 軍儀のゲーム仕様（ルール・UX・カスタマイズ項目）の最終決定。
- 検討枠モジュール（2つ目のゲーム、3D、WCAG申請、2FA、カスタム）の採否をタイミングを見て判断する。
- 各機能の受け入れ条件を subject のモジュール要件文と突き合わせて定義する（例: 通知は「全てのCUDアクション」を満たすか）。
- Privacy Policy / ToS / GDPR フローの内容レビュー（「中身のあるコンテンツ」要件の担保）。
- 評価に向けたデモシナリオの設計と、README の Features List / Modules セクションの内容責任。

### この人が答えられるべき問い
- 「今いくつのモジュールが"デモ可能"か？ 次に完成させるべきものは？」
- 「この実装は subject のモジュール要件文を満たしているか？」

## 2. Project Manager (PM) / Scrum Master

**ミッション**: 「チームが回り続けること」の責任者。障害を取り除き、期限とリスクを管理する。

### subject が求める責務
- チームミーティング・プランニングの主催
- 進捗と期限の追跡
- チームコミュニケーションの担保
- リスクとブロッカーの管理

### 本プロジェクトでの具体的な仕事
- 定例会（週次 or 隔週）の運営、議事録と意思決定ログの記録（評価で「どう組織したか」を説明する材料になる）。
- タスク管理ツール（GitHub Issues 等）の運用: [TASKS.md](./TASKS.md) を Issue 化し、担当者・期限を割り当てる。
- **コミット/PR の分布監視**: 「全員のコミットが履歴に見える」「適切な作業分担」は rejected 事由に直結するため、偏りを早期に検知して作業を再配分する。
- クリティカルパス（軍儀エンジン → ゲーム依存モジュール群）の遅延監視。Phase 1 の遅れは9つのモジュールを道連れにするため最重要リスク。
- ブロッカーのエスカレーション先の整理（技術的判断は Tech Lead、スコープ判断は PO へ）。
- 評価週に向けた逆算スケジュール（模擬評価・README 完成・全端末での動作確認の日程）策定。
- README の Project Management / Individual Contributions セクションの取りまとめ。

### この人が答えられるべき問い
- 「今週のブロッカーは何で、誰が解消するか？」
- 「評価日から逆算して、今のペースで間に合うか？ 落とすなら何を落とすか（→POへ提案）」

## 3. Tech Lead / Architect

**ミッション**: 「どう作るか」の最終責任者。技術的一貫性とコード品質を守る。

### subject が求める責務
- 技術アーキテクチャの定義
- 技術スタックの決定
- コード品質とベストプラクティスの担保
- 重要なコード変更のレビュー

### 本プロジェクトでの具体的な仕事
- 未決定事項の決定を主導: **実装言語/フレームワーク（構成A/B）、AI対戦の実装方式**（PROJECT_OVERVIEW §10）。
- アーキテクチャの番人:
  - サーバー権威モデル（盤面・合法手・勝敗は必ず server 側で判定）の徹底
  - GraphQL（アプリ内通信）と REST 公開 API の二層構成の整合性維持
  - `client/` `server/` `packages/` の境界と依存方向のルール策定
- DB スキーマの設計レビューとマイグレーション運用（「明確なスキーマとリレーション」要件 + README のスキーマ図）。
- 横断的な品質ゲートの整備:
  - CI（lint / typecheck / テスト / **コンソールエラー検出**）
  - FE/BE 両側バリデーションの単一ソース化
  - セキュリティ（パスワードハッシュ、JWT、HTTPS、APIキー、レート制限、アップロードファイルの検証）
- 重要 PR（エンジン、認証、WebSocket 基盤、公開API、コントラクト）の必須レビュアー。
- 技術的意思決定の記録（ADR 的なメモ）。評価での「技術選定の正当化」（README の Technical Stack）の内容責任。
- 「その場修正」評価対策: 全員がコードベースを触れるよう、モジュール構成の説明会・ドキュメント整備を主導。

### この人が答えられるべき問い
- 「なぜこの言語/フレームワーク/DBなのか？」（README にも書く）
- 「新機能Xはどのサービス/レイヤに置くべきか？」

## 4. Developers（全員）

**ミッション**: 機能とモジュールを「評価でデモできる品質」で実装しきる。

### subject が求める責務
- 割り当てられた機能・モジュールの実装
- コードレビューへの参加
- 自分の実装のテスト
- 自分の作業のドキュメント化

### 本プロジェクトでの具体的な仕事
- 担当領域を持ちつつ、**必須パート（認証・DB・コンテナ・バリデーション等）にも全員が貢献**する（subject 明記）。
- 意味のあるコミットメッセージで自分の名義のコミットを残す（rejected 事由対策。他人のアカウントでの push 禁止）。
- 実装と同時に行うこと:
  - FE/BE 両側のバリデーション
  - コンソール warning/error を出さない実装（rejected 事由）
  - 同時利用時の競合を考慮した実装（トランザクション・ロック・冪等性）
  - i18n 対応（ユーザー向けテキストをハードコードしない — Phase 5 で全文言が翻訳対象になる）
- 自分の担当機能について README（Features List / Modules / Individual Contributions）へ記載する材料を提供する。
- **評価対応**: 自分の担当は「デモ + 実装説明 + その場での小修正」ができる状態を維持する。担当外もアーキテクチャレベルでは説明できるようにする。

### 担当領域の割り当て（例・未確定）

チーム人数と得意分野が決まり次第、以下のような領域単位で主担当を割り当てる:

| 領域 | 含まれるモジュール |
|---|---|
| ゲームエンジン・対局 | 軍儀本体、リモート、WebSocket、カスタマイズ、観戦 |
| ソーシャル | ユーザー管理、OAuth、チャット、高度チャット、通知、フレンド |
| 競技システム | トーナメント、統計、検索、ゲーミフィケーション、AI対戦 |
| プラットフォーム | 権限、組織、公開API、ファイル/棋譜、GDPR、export/import |
| 基盤・分析 | Docker/nginx、CI、監視(Prometheus/Grafana)、ダッシュボード、ブロックチェーン、i18n/SSR |

## 6. 評価で全員が説明できること（共通義務）

- 役割がどう分担されたか、自分は何を担当したか
- 作業の組織方法・コミュニケーション方法（ツール・頻度）
- プロジェクト全体のアーキテクチャ概要
- 自分の担当モジュールのデモと実装説明、およびその場での小修正
