全体像はDB全体設計、FEとの接続は認証設計から確認する。以下にチームで確認する事項をまとめる。

## PRで認証について確認すること

1. 初期登録はA案（開発用に即ログイン）とB案（メール確認後にログイン）のどちらで進めるか。
2. メール・パスワード・表示名の3項目と、[認証設計の入力ルール](auth.md#登録項目と入力ルールの提案)でFEを作れるか。一意のユーザー名は別途必要か。
3. 有効期限8時間・自動延長なし・ログアウトは現在セッションのみ、という初期範囲でよいか。
4. `me` を含めて `user` と `expiresAt` を返すAPI案と、Cookie・エラーの扱いで接続できるか。

技術面では、JWTとDBセッションの併用、UUIDv4、認証3テーブル、Cookie・CSRF・試行制限の案をkoyonにレビューしてもらう。A案の入力・保存・認証の契約は具体化したが、メール確認方式とFEの画面要件は合意前である。

## 認証の相談用メッセージ案

> BE基盤は既存のNestJS・GraphQL code-first・Prisma方針で進めたいです。DBは対局・ソーシャル・大会などを含む全体の関係を先に整理し、最初の実装は登録・ログイン・自分の情報取得・ログアウトから進める案です。対局の保存・通信契約も並行して相談したいです。
>
> 認証はメール・パスワード・表示名で登録し、表示名は重複可の案です。入力ルール、認証3テーブル、ログイン期限8時間、現在セッションのログアウト、Cookieとエラーの扱いまで具体化しました。初期版からメール確認を入れるか、入力項目・期限・API応答がFEの要望に合うかを確認したいです。
>
> DBは既存のusers中心の関係図を引き継ぎ、不変のIDで各機能を紐づけます。対局側へは検証済みのユーザーIDを渡す想定なので、SSR・リアルタイム通信との認証のつなぎ方と、各テーブル定義・保存処理の担当も合わせたいです。

## DB全体の提案文

> DBは既存のusers中心の初期案をもとに、認証だけでなく対局・ソーシャル・大会などの関係まで先に整理したいです。初案はこちらで用意し、詳細とマイグレーションは認証・対局から進める想定です。
>
> ユーザーは変更しないIDで紐づけ、表示名やメールが変わっても対戦履歴がつながる形にします。対局は基本情報・参加者・現在状態・操作履歴を分ける案で、復帰と棋譜再生に必要な情報を確認したいです。
>
> まず対局保存の形式、FEへ渡す契約、復帰時の時計、各テーブル定義と保存処理の担当を相談したいです。メール変更・削除・再勝負などの未決定事項も資料に記載しました。
