メール変更、パスワード再設定、OAuth、全端末からのログアウトは、この4操作の後に追加する機能とする。一般公開の前にはメール確認・アカウント復旧の提供範囲も確認する。

### 登録項目と入力ルールの提案

| 項目 | 必須・長さの初案 | 扱い |
|---|---|---|
| `displayName` | 必須、前後の空白除去・NFC正規化後に1〜30 Unicodeコードポイント | 重複可。元の入力に `Cc`・`Cf`・`Zl`・`Zp` があれば拒否してから正規化し、空白だけの入力も拒否する。詳細は下記 |
| `email` | 必須、初期版はASCIIのメール形式、正規化後254文字以内 | 前後の空白を除き、小文字へ統一して保存・検索。大文字小文字を区別しないことをアプリの規則とする。内部空白は拒否し、プロバイダー固有のドット除去や `+` 以降の削除はしない |
| `password` | 必須、NFC正規化後に15〜64 Unicodeコードポイントを初期案とする | 空白・日本語を許可。大文字・数字・記号の組み合わせは強制しない。NFC以外の変換、前後の空白除去・大小文字変換・切り詰めをしない |

表示名は、Unicodeの `Cc`（制御文字）、`Cf`（書式制御文字）、`Zl`（行区切り）、`Zp`（段落区切り）を初期案の拒否対象とする。ゼロ幅スペース・BOM・双方向制御も含め、削除して受け入れるのではなく入力エラーにする。`Cf` のZWJ/ZWNJも拒否するため、ZWJを使う家族絵文字などは使えない。単体の絵文字は他の条件を満たせば使える。この制約はFEと合意し、パスワードへは流用しない。[Unicodeの文字カテゴリ](https://www.unicode.org/reports/tr44/#General_Category_Values)

表示名の上限・メールの対応範囲は画面側と相談する提案値。メールのローカル部まで小文字にするのは、このアプリのログイン名の規則であり、すべてのメールサービスが大小文字を同一視するという意味ではない。国際化メールへの対応を求める場合は、正規化・入力仕様を変更する。[メール検証の考慮点](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)

パスワードポリシーは [OWASPのパスワード指針](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls) を基にする。MFAなしでは最低15文字、最大長は少なくとも64文字を許容する指針に沿い、このアプリの初期案を15〜64文字とする。長さはNFC正規化後のUnicodeコードポイント数で数え、合意後は正規化・最小最大文字数・数え方を `packages/shared` の1か所に定義して、FEの表示・検証とBEの判定を揃える。

登録・ログインとも、BEで共有関数によるNFC正規化 → 長さ等の検証 → 正規化した値のハッシュ化・照合、の順に処理する。`が` と `か + U+3099` のように正規化後が同じ入力を同じパスワードとして扱う。確認用入力の比較も同じ正規化後に行う。互換文字まで同一化するNFKC/NFKDは採用せず、空白・大小文字は維持する。根拠は旧版ではなく、[NIST SP 800-63B-4 §3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver) のNFC推奨とする（参照日: 2026-10-13）。初回実装から統一し、将来この方式を変える際は保存済みハッシュとの互換性を確認する。

よく使われる・漏えい済みのパスワードを拒否するチェックも登録時にBEで行い、NFC正規化後の値を照合対象にする。照合用リストの提供元・更新方法は実装時に選び、パスワード平文を外部へ送らない。

上記の登録用ルールを `packages/shared` にまとめ、FEとBEの両方で利用する。ログイン入力はメールの正規化とパスワードのNFC正規化・必須・最大文字数を確認してから、保存済みハッシュと照合する。最大文字数は登録・ログインで同じ共有定義を使い、登録用の最低文字数や禁止リストはログイン時に再適用しない。合意した文字数ルールは当面固定し、変更が必要になった時点で既存利用者のログインへの影響と、必要な移行方法を確認する。

確認用パスワード欄を置く場合、一致確認はFEの入力補助とし、APIへ送るパスワードは1つ。入力値、GraphQL variables、Cookie、JWTはログへ記録しない。

## GraphQLの入出力案

操作名と型名は提案。code-firstのTypeScript定義を正本とし、GraphQLスキーマを生成する。

| 操作 | 入力 | 正常時の結果 | 補足 |
|---|---|---|---|
| `signUp` | `email`、`password`、`displayName` | `AuthPayload` | 未ログイン時のみ許可。A案では登録とセッション作成後にCookieを設定する |
| `signIn` | `email`、`password` | `AuthPayload` | Cookieを設定する。JWTを応答本文には含めない |
| `me` | ユーザーIDの指定なし。Cookieで認証 | `AuthPayload` または `null` | 未ログイン・不正なCookie・期限切れ・失効済みは `null`。DB障害等を未ログイン扱いにはしない |
| `signOut` | ユーザーIDの指定なし。Cookieで認証 | `success: true` | 現在のセッションを失効させ、Cookieを解除する。既に未ログインでも成功とする |

初期版では `signUp`・`signIn`・`signOut` をそれぞれ単独で呼ぶ。認証mutationを含む実行対象の操作では、トップレベルのフィールドをその認証フィールド1つに限定する（`__typename` を除く）。複数の認証操作や、他の更新処理との混在は `VALIDATION_FAILED` で拒否する。alias・フラグメント・ディレクティブも考慮して実行対象を確認し、どの更新処理も始める前に拒否する。HTTPバッチ（配列形式の要求）は初期版では無効とし、HTTP 400で全体を拒否する。

これは1回の要求内でログイン状態を切り替えた後、別の処理が要求時の古いCookieを使うことを避けるための制限。拒否時はユーザー・セッションを変更せず、Cookieも設定・解除しない。

| 型 | 項目案 | 公開先 |
|---|---|---|
| `Viewer` | `id: ID!`、`displayName: String!`、`email: String!` | ログイン中の本人 |
| `PublicUser` | `id: ID!`、`displayName: String!` | 他人に見せる場面。必要なAPIを追加する段階で実装 |
| `AuthPayload` | `user: Viewer!`、`expiresAt: DateTime!` | ログイン中の本人と、そのセッションの有効期限 |

`!` はnullにならない値を表す。パスワードハッシュやセッションの内部情報は、どの公開型にも含めない。

`DateTime` はUTCの日時を返すスカラーとする。FEが期限を把握できるように `expiresAt` を追加し、`me` も `AuthPayload` に揃える提案。従来案の `me { id }` は `me { user { id } expiresAt }` に変わるため、型生成前にFEと合意する。期限の最終判定はBEが行う。

入力は `SignUpInput { email: String!, password: String!, displayName: String! }`、`SignInInput { email: String!, password: String! }` をそれぞれ `input` 引数で渡す。入力の `null`・必須項目不足はGraphQLの入力検証で拒否する。`signOut` の戻り値は `SignOutPayload { success: Boolean! }` とする。

```graphql
mutation SignUp($input: SignUpInput!) {
  signUp(input: $input) {
    user { id displayName email }
    expiresAt
  }
}

query Me {
  me {
    user { id displayName email }
    expiresAt
  }
}
```

上記は提案する操作例であり、生成済みスキーマで検証したものではない。

後続のプロフィール更新では「項目を送らない＝変更しない」を基本にする。任意項目の削除には `null` を使う案とし、空文字の扱いは項目ごとに定義する。必須の表示名は `null` を受け付けない。

### エラーとFEの表示

アプリが返すエラーは `errors[].extensions.code` で区別する案とする。項目別エラーはフィールド名と検証コードを返し、FEが表示言語に合わせた文言へ変換する。GraphQL自体の構文・型エラーの扱いも、基盤導入時に確認する。

| コード案 | 意味 | FE側の対応例 |
|---|---|---|
| `VALIDATION_FAILED` | 文字数・形式などの入力違反、認証操作の禁止された組み合わせ | 項目別エラーは対象の入力欄に、要求全体のエラーは画面に説明を表示 |
| `ALREADY_AUTHENTICATED` | ログイン中の新規登録 | 現在のログイン状態を維持し、新規登録には先にログアウトが必要と案内 |
| `REGISTRATION_FAILED` | メール重複などで登録できない | 登録を完了できない旨と、ログイン等の導線を表示 |
| `INVALID_CREDENTIALS` | ログイン情報が正しくない | メールの存在・パスワード誤りを区別しない表示 |
| `UNAUTHENTICATED` | 認証が必要な操作への未認証要求 | ログインへ案内。`me` は上記のとおり `null` |
| `FORBIDDEN` | 認証済みだが操作権限がない | 操作できない旨を表示 |
| `RATE_LIMITED` | 登録・ログインの試行が多すぎる | `retryAfterSeconds` を使い、再試行まで待つよう表示 |
| `INTERNAL_SERVER_ERROR` | 予期しない障害 | 再試行の案内。内部例外やSQLを公開しない |

項目別の形式は、例えば `extensions: { code: "VALIDATION_FAILED", fieldErrors: [{ field: "displayName", code: "TOO_LONG" }] }` とする。入力値やパスワードをエラーへ含めない。HTTPの失敗・通信断とGraphQLの `errors` はそれぞれFEで扱い、すべての失敗を「未ログイン」に変換しない。

存在しないメールとパスワード誤りは同じログインエラーを返す。存在しない場合もダミーハッシュの照合を行い、処理時間の大きな差を避ける。A案は成功時に即ログインするため、登録の成功・失敗からメールの登録有無を推測できる余地がある。重複エラーの文言だけではこの性質は解消されず、公開前の登録フローの判断に含める。

試行制限はBEでパスワード照合前に行う。初期値の案はログインが正規化済みメール識別子ごとに5回/分・IPごとに30回/分、登録がIPごとに5回/10分。共有回線の利用と負荷を測って調整し、永久ロックにはしない。上記の単独実行条件を満たした認証操作ごとに試行を数え、alias名を変えても別の制限枠にはしない。複数操作・HTTPバッチは実行前に拒否する。

接続元IPは次の規約で取得し、認証とリアルタイム通信で共有する。

- BEが受けたTCP接続の相手を確認し、運用設定で指定したnginxの接続元だけを信頼する。その場合だけ、nginxが `$remote_addr` で上書きした `X-Real-IP` を単一のIPとして検証・正規化して使う。欠落・複数値・不正な形式は拒否し、別ヘッダーへフォールバックしない。
- nginx以外からの接続では転送ヘッダーを無視し、ソケットの接続元IPを使う。プライベートIP全体を信頼する設定、`trust proxy = true`、XFFの先頭採用はしない。許可するnginxのアドレスはコンテナ再作成時も更新できるよう構成する。[Expressのプロキシ信頼設定](https://expressjs.com/en/guide/behind-proxies/)
- 現在のnginxは `/graphql` に `X-Real-IP` を上書きする一方、XFFにはクライアントが送った値も残す。IP判定にはXFFを使わない。BEのポートは外部公開せず、登録・ログインはnginx経由に限定する。内部SSRは後述の `me` の読み取りと区別し、nginx以外からの認証mutationは拒否する。

制限カウンタは、開発用の単一BEプロセスでは期限付きメモリを使う案とし、同時要求の判定・加算を分離しない。再起動ではカウンタが消え、複数プロセスでは共有されない制約がある。一般公開または複数プロセス化の前には共有ストアへ移し、再起動・並列要求でも同じ制限枠を使う方式を合意・検証する。開発用のメモリ制限を本番の保証とはしない。

FEへスキーマ・操作例・仮の応答を先に渡せば、BE完成前でも画面を進められる。型生成が成功することと、実際のAPIが動くことは別に検証する。

## DBの論理設計案

既存の [全体概要 §6 のDB関係図](../PROJECT_OVERVIEW.md) の `users` を各機能の接続点とする。以下は全体設計のうち、最初の認証に必要な部分。現在の [Docker Compose](../../docker-compose.yml) はPostgreSQL 16なので、IDは内蔵の `gen_random_uuid()` によるUUIDv4を初案とする。[PostgreSQL 16のUUID生成](https://www.postgresql.org/docs/16/functions-uuid.html)

| テーブル案 | 主な保存項目 | 制約と理由 |
|---|---|---|
| `users` | 不変のID、メール、表示名、作成・更新日時 | IDは主キー。合意した正規化ルールに従うメールに一意制約を設け、同時登録でも重複を防ぐ。表示名は識別に使わない |
| `password_credentials` | ユーザーID、パスワードハッシュ、更新日時 | ユーザーIDを主キー兼外部キーにし、ユーザー1人につき最大1件。認証情報をプロフィールから分離し、将来パスワードを持たないOAuthユーザーにも対応できる構成にする |
| `auth_sessions` | セッションID、ユーザーID、有効期限、失効日時、作成日時 | ユーザーに対して複数件。JWTにセッションIDを含め、検証時に期限・失効状態・ユーザーとの対応も確認する案。JWT本文の保存は不要 |

初回マイグレーションへ落とす列の案は以下。B案を選ぶ場合のメール確認テーブルは、この3テーブルに追加する。

| テーブル | 列・型・NULLの扱い | 初期値・制約 |
|---|---|---|
| `users` | `id: uuid`、`email: text`、`display_name: text`、`created_at / updated_at: timestamptz` は必須。`email_verified_at: timestamptz` は任意 | ID主キー、正規化済みメール一意。日時は登録時に設定し、更新日時は更新処理で進める。メール確認前は `email_verified_at = null` |
| `password_credentials` | `user_id: uuid`、`password_hash: text`、`updated_at: timestamptz`、すべて必須 | ユーザーIDを主キー・外部キーにする。ハッシュ形式にはソルトと計算パラメーターも含まれる |
| `auth_sessions` | `id / user_id: uuid`、`created_at / expires_at: timestamptz` は必須。`revoked_at: timestamptz` は任意 | ID主キー、ユーザーID外部キー。`expires_at > created_at`、失効日時は作成日時以降。`user_id` と期限切れ削除用 `expires_at` に索引を置く |

期限切れセッションはBEの保守ジョブで起動時と1時間ごとに削除する案とする。DB時刻で `expires_at <= 現在時刻` の行だけを `expires_at` 索引で少量ずつ取得し、短いトランザクションで削除する。失効済みの行も元の有効期限までは残し、期限後は監査履歴として保持しない。監査が必要になれば別の保存要件を決める。削除失敗は秘密値を含めず記録し、次回に再試行する。複数回実行しても有効なセッションを消さない。

削除ジョブは容量管理であり認証判定の代わりではない。削除が遅れても期限・失効は毎回検証し、既に削除されたセッションIDも未認証として扱う。

必須・一意・外部キーに加え、表示名の保存後の長さ、メールの長さ・正規化済みであることをDBの制約でも確認する。形式などの詳しい入力検証は共有ルールとBEで行う。Prismaで表せない制約はマイグレーションSQLに記載する。

認証2テーブルからユーザーへの削除時動作は、初案では `RESTRICT` とする。後続の削除機能でセッション・認証情報を処理してからユーザーを削除する。対局などの保持・匿名化まで含めた削除方針の確定前に、ユーザー削除APIは作らない。

```text
users 1 ── 0..1 password_credentials
      1 ── 0..N auth_sessions
      1 ── 0..N oauth_accounts（後続）
```

初期のメール登録では `users` と `password_credentials` を必ずセットで作る。一連のDB更新をトランザクションで扱い、片方だけが残ることを防ぐ。

### 登録・ログインの保存順序

1. GraphQLの単独実行条件、入力検証、試行制限を確認する。
2. 登録時はCookieの認証状態を確認する。有効なセッションがあれば `ALREADY_AUTHENTICATED` で拒否し、ユーザー・認証情報・セッションを作らず、既存セッションとCookieも変更しない。Cookieなし・不正・期限切れ・失効済みは未ログインとして扱う。セッション検証に必要なDBアクセスが失敗した場合は、未ログインとみなして登録を続けず、障害を返す。
3. 登録時のハッシュ計算・ログイン時のハッシュ照合は、DBのトランザクションを長く保持しないようその外で行う。
4. 登録ではユーザー・認証情報・A案のセッションを同じトランザクションで作る。メールの事前検索だけに頼らず、一意制約の競合を登録失敗として扱う。
5. ログイン成功時は新しいセッションIDを発行する。そのブラウザの有効な旧Cookieが指すセッションは、新セッション作成と同じトランザクションで失効させる。他端末のセッションは維持する。ログイン失敗時は既存のセッションを変更しない。
6. DB確定後に新しいCookieを返す。保存に失敗したら成功応答・ログインCookieを返さない。DB確定後に応答が失われた場合、再登録でアカウントを増やさず、ログインから復帰できるようにする。

パスワードはArgon2idでハッシュ化する。初期パラメーターの基準はメモリ19 MiB・反復2・並列度1とし、コンテナ上の処理時間・同時負荷を測って調整する。ユーザーごとにランダムなソルトを使い、平文の保存や独自のハッシュ比較をしない。[OWASPの保存方式](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#argon2id)

日時はタイムゾーンを扱える型を使う。`auth_sessions.user_id` は外部キーと検索用インデックスを設ける。主キー・一意制約で検索が支えられる列には、同じインデックスを重複追加しない。

将来の `oauth_accounts` はプロバイダーとそのユーザー識別子で関連づける。メールが同じという理由だけで既存アカウントに自動連結する設計にはしない。

メール変更時も `users.id` は維持する。確認中の新しいメールは別の申請として保存し、再認証とメール確認を経て更新する案とする。OAuthでメールを取得できない利用者を受け入れるかは未決定であり、受け入れるならDBの必須条件と `Viewer.email: String!` を合わせて見直す。詳細は全体設計案に記載する。

ユーザー削除時の対局・メッセージの保持や匿名化は、各担当とGDPR対応の範囲で決める。全関連データを一律に連鎖削除する方針は置かない。

## ログイン状態・Cookieの詳細案

JWTは本人とセッションを示す署名付きの値。DBのセッションは「そのログインを今も許可しているか」を管理する。署名の確認だけでは、有効期限前にログアウトしたJWTを無効にできないため、両方を確認する。

| 項目 | 初案 |
|---|---|
| 有効期限 | 発行時から8時間。JWTの `exp`、DBの `expires_at`、Cookieの期限を揃える。初期版は自動延長・refresh tokenなし |
| 複数端末 | 別のログインは別セッション。同じブラウザのタブはCookieを共有する |
| Cookie | 名前は `__Host-session`。`Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/`、`Domain` 指定なし |
| JWTの内容 | `sub` にユーザーID、`sid` にセッションID。`iat`・`exp`・`iss`・`aud` を設定し、本人情報・メール・パスワードは入れない |
| JWTの検証 | 許可する署名方式を固定し、署名・期限・発行者・宛先を検証。DBのセッションと `sub` の対応、有効期限、未失効を確認 |
| 署名鍵 | 環境変数から供給。未設定や `.env.example` の仮値では起動を失敗させる。方式・鍵の更新手順は実装時に確定 |
| ログアウト | 現在のセッションを失効してCookieを解除。失効済み、期限切れ、Cookieなしは成功。DBにアクセスすべき状況でDBが失敗したら、完了したことにしない |

8時間はチームへ出す提案値で、標準で決められた値ではない。対局中でも期限はBEで判定するため、期限切れ後の操作を拒否し、再ログイン後に同じユーザーとして復帰する。時計・切断猶予は対局の規則に従う。初期版は操作間隔による追加の自動ログアウトを設けず、長考中に認証を切ることを避ける。[セッション期限の考え方](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#automatic-session-expiration)

### ブラウザ・SSR・リアルタイムとの接続

現在の [nginx設定](../../infra/nginx/nginx.conf) はFEと `/graphql`・`/socket.io/` を同じ公開URLにまとめている。初期版はこのHTTPS経由で接続を確認する。

- `/graphql` のすべてのquery・mutation（`me`、登録・ログイン・ログアウト、後続の状態変更を含む）はPOST・`application/json` に限定し、`X-App-Request: 1` を必須にする。BEの共通ミドルウェアでResolver実行前に検査する。GET等は405、非対応のContent-Typeは415、ヘッダー欠落・値の不一致は403で拒否し、副作用やCookieの変更を起こさない。OPTIONSはCORSの事前確認だけに使い、GraphQL操作を実行しない。
- `Origin` がある場合は設定した公開Originと完全一致を確認し、別Origin・文字列 `null` は403で拒否する。比較元は環境設定とし、要求のHostや転送ヘッダーから作らない。CORSはそのOrigin・POST・必要なヘッダーだけを許可し、任意のOriginやワイルドカードを許可しない。Originなしのサーバー間要求も上記のメソッド・Content-Type・ヘッダー検査と通常の認証・認可を通す。
- このヘッダーは秘密値や本人確認ではなく、ブラウザのクロスオリジン送信を制限するための条件。Cookieの `SameSite` だけに依存せず、別サイトから状態変更を起こすCSRFを防ぐ。[APIのカスタムヘッダーによるCSRF対策](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi)
- Apolloの `csrfPrevention` も有効に保つ。ただし組み込み機能は `application/json` だけでも条件を満たすため、`requestHeaders` に独自ヘッダーを列挙するだけでは必須化できない。共通ミドルウェアがアプリの厳密な条件を担い、組み込み機能は追加の防御とする。Apolloはまだ未導入なので、導入時のバージョンで挙動を確認する。[ApolloのCSRF対策](https://www.apollographql.com/docs/apollo-server/security/cors#preventing-cross-site-request-forgery-csrf)
- SSRから `me` を呼ぶ場合は、今のリクエストの認証Cookieと必要なヘッダーを渡し、応答を利用者間で共有キャッシュしない。初期版の登録・ログイン・ログアウトは公開URLのnginxを経由してブラウザから呼び、Cookieをブラウザに設定する。内部呼び出しでOriginを省略する扱いは、上記のヘッダー必須条件を維持して確認する。
- Socket.IOのpollingは、すべてのGET/POSTで `X-App-Request: 1` を必須にし、FEが `extraHeaders` で付ける。Originがあれば公開Originと完全一致を確認し、`null`・別Originを拒否する。同一OriginのGETはOriginが付かないことがあるため、欠落だけでは拒否せず独自ヘッダーと認証を確認する。CORSは公開Origin・GET/POST・必要なヘッダーだけを許可し、OPTIONSでは接続・操作を実行しない。[Originの送信条件](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin#description)
- WebSocketの初回接続・upgradeではOriginを必須とし、欠落・`null`・別Originを拒否する。ブラウザWebSocketには独自ヘッダーを要求しない。これらはpollingの各HTTP要求とWebSocket接続要求の入口で検査し、Socket.IOのアプリ用接続処理だけには置かない。[Socket.IOの追加ヘッダー](https://socket.io/docs/v4/client-options/#extraheaders)
- どちらの通信でも接続時に認証し、各操作でセッションの有効性を確認する。ログアウト・期限切れ後は保護された配信からも外し、接続が残っているだけで認証成功としない。
- 現在のnginxの `/socket.io/` にはIP・プロトコル転送の設定がない。接続実装時に `X-Real-IP $remote_addr` と `X-Forwarded-Proto https` の上書きを追加し、BEでは上記の信頼した接続元からの値だけを使う。設定追加前にSocket.IOの転送ヘッダーを信頼しない。ブラウザWebSocketへGraphQL用の独自ヘッダーを要求する設計にはしない。
- FEはログアウト後に本人情報・保護された画面のキャッシュを消す。通信断やDB障害では直ちに未ログイン表示へ切り替えず、再試行を案内する。

この接続条件はkoyonと実装前に確認し、別Originでの開発、GraphQLのGETやファイルアップロードを追加する場合はCSRFの条件も見直す。

## 認証と対局担当への渡し方

```text
FEの要求と認証Cookie
  → Auth側がJWTの署名・期限とセッションを検証
  → 検証済みのユーザーIDを処理へ渡す
  → Match側が対局参加者・手番・受け付けてよい操作かを確認
  → エンジンが合法手を判定
```

FEが指定したユーザーIDを本人確認には使わない。Auth側は「誰か」を保証し、Match側はそのユーザーを対局の黒・白に対応づける。エンジンの `Move.player` にクライアントの申告をそのまま渡さない。

時間切れの確定や合意引き分けはサーバー側の責務であり、クライアントがエンジンの全操作を直接指定できるAPIにはしない。根拠は [軍儀ルール §11.6・§11.7](../GUNGI_RULES.md)。

JWTをCookieで扱うため、HTTPS・HttpOnlyに加えて、Cookieの送信条件とCSRF対策を認証実装に含める。Cookieの解除だけで完了とせず、対応するセッションも失効させる。パスワード・JWTをログへ出さない。

次の接続条件はkoyonと合わせる。

- Next.jsのSSRから本人情報を取得するときのCookieの受け渡しと、利用者ごとの情報を共有キャッシュに載せない扱い。
- Socket.IOとGraphQL Subscriptionsの用途分担。既存資料では記述が揃っていない。
- リアルタイム接続で同じ認証判定を使う方法と、接続中にログアウト・期限切れになった場合の扱い。
- エンジンのデータ形式を引き継ぐ範囲と、対局状態・棋譜の保存責任。Auth側ではゲームルールを再実装しない。
