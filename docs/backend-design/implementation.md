## 認証

### 合意後の実装順と確認すること

先に全体設計案の関係・担当の境界を確認し、以下の認証基盤を実装する。対局の詳細設計とFEの通信契約は並行して相談し、合意後に対局用マイグレーションと保存処理を追加する。

| 順序 | 成果物 | 動作で確認すること |
|---|---|---|
| 1 | ユーザー・認証のPrisma定義、初回マイグレーション、ER図 | 空の開発DBに適用できる。外部キー・一意制約が機能する |
| 2 | GraphQL基盤、共有入力ルール、スキーマ生成・FE用型生成 | FEの操作例から型を生成できる。入力ルールの正本と生成物の関係が明確 |
| 3 | 登録・ログイン・`me`・ログアウト | 登録からログアウトまで接続できる。不正な入力、誤ったパスワード、期限切れ、失効済みセッションを扱える |
| 4 | FEとの接続、起動・マイグレーション手順 | 別の開発環境でも起動・登録・ログインできる。Cookieとエラー表示をブラウザで確認できる |

マイグレーションは開発用DBで確認する。共有DBへの適用は対象と既存データへの影響を確認して行う。チームに共有済みの変更は、新しいマイグレーションで進める。

#### 認証が完成したと判断するための確認

以下は実装時の受け入れ条件であり、現時点で動作確認した結果ではない。

| 場面 | 期待する結果 |
|---|---|
| 表示名の境界値、表示名・パスワードの日本語・絵文字・空白 | FEとBEが同じルール・コードポイントの数え方を使う。パスワードはNFC以外の変換・空白除去・大小文字変換・切り詰めをしない |
| 表示名に `Cc`・`Cf`・`Zl`・`Zp` を含める | 前後の改行、ゼロ幅スペース、BOM、双方向制御、ZWJ入り絵文字を削除して通さず拒否する。通常の日本語や単体絵文字は他の条件を満たせば通る |
| NFCで登録してNFDでログイン、その逆 | 同じ正規化後のパスワードでログインできる。FE・BEともNFC後に数え、合成文字を含む入力でも下限・上限の判定が一致する |
| 登録時のNFC正規化後のパスワードが14・15・64・65文字 | 長さの判定は15・64文字を通し、14・65文字を拒否する。強度など長さ以外の条件は満たす入力で確認する |
| 登録後に同じパスワードでログイン | 下限・上限を含む登録可能なパスワードでログインできる。ログインでも空入力・上限超過を拒否する |
| Aでログイン中にBの新規登録を要求 | `ALREADY_AUTHENTICATED` で拒否する。Bのユーザー・認証情報・セッションは作らず、AのセッションとCookieを維持する |
| 登録前のCookie検証でDB障害 | 未ログインとして続行せず障害を返す。新規登録・Cookie変更を行わない |
| 同じメールを大文字小文字を変えて同時登録 | 正規化後の一意制約で1人だけ作成される。失敗した処理の認証情報・セッションが残らない |
| 登録の途中で保存失敗 | ユーザー・認証情報・セッションが部分的に残らず、Cookieを発行しない |
| 存在しないメール、誤ったパスワード | 同じログインエラー。入力値・ハッシュ・内部例外を応答へ含めない |
| 正常なCookie、不正な署名、期限切れ、失効済み | 正常時だけ本人情報を返す。不正・期限切れ・失効済みは保護操作を拒否し、`me` は `null` |
| 有効なJWTを保持したままログアウト後に再利用 | DBで失効したセッションなので保護操作を拒否する。他端末のセッションは維持する |
| 有効なCookieでアクセスした際のDB停止 | ログアウト成功・未ログイン扱いにせず、障害として返す |
| 期限直前・同時刻・直後と失効済みセッションを用意して削除ジョブを複数回実行 | 期限切れだけを削除し、失効済みでも元の期限前の行は残す。有効なセッションは維持し、削除済みIDの再利用は未認証になる |
| 削除ジョブ失敗後に再起動・次回実行 | 起動時・定期実行で回収できる。削除待ちの期限切れ・失効済みセッションも認証を通らない |
| 全GraphQL操作へ別Origin・`null` Origin・独自ヘッダーの欠落や不正値を送る | `me`・認証操作・後続mutationを共通条件で拒否し、Resolver・Cookie変更を実行しない。許可したFE操作とOriginなしのSSR本人取得は必要ヘッダー・認証付きで動く |
| JSONだけ、Apollo標準ヘッダーだけ、フォーム、GET、OPTIONSを送る | JSONでも `X-App-Request: 1` がなければ拒否。フォームは415、GETは405。OPTIONSは許可Originの事前確認のみで、操作を実行しない |
| nginx経由でXFF・`X-Real-IP`を偽装する | nginxが上書きした接続元だけでIP制限枠に数える。BEへ直接送った認証mutationは拒否し、その他の内部要求でも転送ヘッダーを信用しない |
| 同時試行、BE再起動、複数プロセスの制限枠 | 単一プロセスで上限を超えて通らない。開発用メモリは再起動でリセットされる制約を確認する。公開・複数プロセス化前には共有ストアで制限枠を維持するテストを追加する |
| 1つのmutationに `signIn` と `signOut`、複数の `signIn`、認証と他の更新処理を含める | alias・フラグメント・ディレクティブを使っても、複数の処理が実行対象なら実行前に全体を拒否する。最初の処理だけ実行されたり、Cookieだけ変更されたりしない |
| HTTPバッチで認証操作を送る | HTTP 400で全体を拒否し、ユーザー・セッション・Cookieを変更しない |
| 単独の認証操作をalias名を変えながら繰り返す | 同じメール識別子・IPの制限枠に数え、ハッシュ処理を無制限に増やせない |
| 利用者A・BのSSRとログアウト | 本人情報が共有キャッシュから混ざらず、ログアウト後に保護情報を表示し続けない |

リアルタイム接続は対局との結合時に、Originのない同一Originのpolling GETが独自ヘッダーと有効なCookieで接続できること、pollingのヘッダー欠落・不正値と両経路の `null`・別Originが拒否されることを確認する。WebSocketの初回接続・upgradeはOrigin必須とし、独自ヘッダーなしで正常接続できることを確認する。nginxによるIP・プロトコルの上書き、各polling要求の検査、接続後の期限切れ・失効の反映も対象とする。B案を選んだ場合は、メール確認トークンの誤り・期限切れ・再利用・再送・確認前のログイン拒否を追加する。

### 実装を読む順番

登録機能では、入力例 → Resolver → Service → Prisma → DB制約 → 応答の順に追う。認証が必要な操作では、その前にGuardの本人確認を読む。

各実装単位で、次を説明できることを理解確認の目標にする。

- 何を受け取り、何を返すか。
- なぜそのテーブル・列・関係が必要か。
- どこで入力・本人・権限を確認するか。
- 失敗や同時操作が起きたとき、何が保存され、何が拒否されるか。
- テストがどの仕様を確かめているか。

## DB・対局

### 合意後に実装・検証する順番

1. ID・メール・認証の入力条件を確定し、ユーザー・認証のPrisma定義とマイグレーションを作る。
2. GraphQL基盤と型生成を整え、登録・ログイン・本人情報取得・ログアウトをFEにつなぐ。
3. 対局担当と合意した保存モデルを追加し、参加・開始・着手・終局・再接続をつなぐ。認証実装と並行して仕様を詰められる。
4. ソーシャル・大会・統計などの担当と、各領域のマイグレーションを追加する。共有後の変更は既存マイグレーションの書き換えで処理しない。

実装時の重点確認は、空DBへの適用、メール同時登録の拒否、メール変更後の参照維持、非参加者の着手拒否、同時着手と同じ要求の再送、保存途中の失敗、DB確定後に応答が失われた場合の復帰、棋譜再生と保存状態の一致。現時点では未実装・未検証。

時計については、期限直前・同時刻・直後の新規着手、ロック待ち中の期限切れ、タイマー処理を遅延させた状態での期限後の着手を確認する。期限後の着手は盤面へ反映されず、時間切れの結果・状態・イベントが一緒に保存されることを確認する。着手とタイマーの競合でも終局は1回だけとし、手番が進んだ後の古いタイマーは最新の時計を確認する。着手がなくてもタイマーで終局すること、受理済みの要求の再送では時計判定や状態更新を再実行しないことも確認する。

| 復旧・終局の場面 | 期待する結果 |
|---|---|
| タイマー待機中に再起動し、以後クライアントが操作しない | 期限前なら元の期限で復元し、停止中に期限を過ぎていれば起動時に終局する。再起動時刻を基準に持ち時間を延長しない |
| 状態保存直後・タイマー設定前に停止、またはDB障害後に復帰 | 起動時・定期走査で回収し、期限超過の着手は通さない。DBへ書けない間に成功応答を返さない |
| 複数の走査処理と着手・古いタイマーが競合 | 最新の保存期限を使い、終局イベントと勝敗を1回だけ確定する。終局後の期限は `null` |
| 配置から対局へ進む、切断する、操作を続ける | 初期案では有限の持ち時間が必ず減り、フェーズ遷移・切断で停止・リセットしない。無操作がなくても有限時間で終わる |
| 持ち時間なし・無限値・加算ありを指定して開始 | 初期案の範囲外として拒否する。時計なしを追加する際は、操作で延長できない対局全体の期限と終局結果の受け入れ条件を合意してから許可する |

配信失敗の確認では、DB確定後の配信を1回欠落させ、接続を維持したまま追加の着手を行わない条件も含める。定期確認によって両者の表示が保存済みの状態へ揃い、イベントの二重適用や古い版への巻き戻りが起きないことを確認する。
